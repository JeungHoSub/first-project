## 발견 사항

### 높음
- **H1. 실행 장소가 정해지지 않음** (spec 12절 "사용자의 PC 또는 클라우드 세션", 10절 원본 영상 git 제외, 11절 secrets git 제외)
  - 원본 영상은 사용자 PC에 있고, 토큰은 git에 못 올리고, 클라우드 세션은 끝나면 사라진다. 클라우드 세션에서는 원본에 접근도, 브라우저 로그인(OAuth)도 안 된다. 즉 "렌더와 업로드를 어디서 돌리는가"가 비어 있어 로드맵 1-4, 1-8, 1-10이 그대로 실행될지 불확실하다.
  - 제안: 사용자 질문 4번에 "실행 장소"를 추가. 추천안 예: 후보·계획·메타는 클라우드 세션에서, 렌더·업로드는 사용자 PC에서 실행(원본과 토큰이 PC에 있으므로). 이에 맞춰 12절을 확정.
- **H2. 승인이 "어떤 파일에 대한 승인인지" 묶여 있지 않음** (spec 8절 `approval.yaml`, 11절 `--approval`)
  - 승인 후 영상이나 메타가 바뀌어도 approved면 업로드될 수 있다. 2단계 "배치 승인"에서는 승인 뒤 항목이 섞여 들어갈 위험도 있다.
  - 제안: `approval.yaml`에 승인한 `short_id`, `file_sha256`, `title` 기록. 업로더는 현재 파일 해시와 일치할 때만 허용. 배치 승인은 쇼츠 ID 목록을 명시.

### 중간
- **M1. 중복 방지 기록의 보존** (spec 11절): 중복 판단 근거인 `upload-log.csv`가 커밋 대상이다. 업로드 직후 커밋 전에 세션이 끝나면 기록이 사라져 재업로드 위험. 제안: 업로드 성공 즉시 로그 커밋을 절차에 넣거나, 업로드 전 YouTube 쪽 목록 조회로 이중 확인.
- **M2. 비밀·권한 보강** (spec 10절 .gitignore 목록, roadmap 0단계)
  - 목록에 `projects/shared/uploader/state/`와 실제 `uploader.yaml`(예시만 커밋할 경우)이 빠져 있다. 현재 `.gitignore`는 `*.mp4`, `client_secret*.json`, `token*.json`은 있으나 `secrets/`, `work/`, `state/`는 확인 안 됨(총괄이 추가한다고 되어 있으니 0단계 전에 반영).
  - OAuth 동의 화면이 "테스트" 상태이면 토큰이 짧은 기간(알려진 바로는 약 7일) 뒤 만료돼 자동화가 끊길 수 있다. 일반 지식이라 공식 확인 필요. roadmap 0단계에 "토큰 만료 여부 실측"을 추가 권장.
- **M3. brief 전제와 리서치 불일치**: brief 목표의 "설명란·고정 댓글에 본편 링크"는 리서치상 불확실(링크 클릭 불가 가능, 고정 댓글 API 미확인). spec 8절은 올바르게 대체(관련 동영상 수동 연결). 제안: 총괄이 사용자 답변 반영 때 brief 문구를 "관련 동영상 연결(수동) + 설명란에 본편 제목 텍스트"로 갱신.
- **M4. 템플릿 명확성** (spec 5절)
  - (a) "YAML 블록 하나당 후보 하나"라고 했는데 템플릿은 블록 하나에 후보 목록. 규칙 문구 또는 템플릿 중 하나로 통일.
  - (b) 파일 상단 `source_video`가 1개뿐이다. 영상이 여러 편인 프로젝트(에피소드 여러 개)는 `source_videos:` 목록으로 하고 `single` 후보에도 `video_id`를 넣어야 한다.
  - (c) `source_video.path` 예시가 저장소 안 경로(`projects/.../final.mp4`)인데 10절은 원본을 git 밖(사용자 PC)에 둔다고 한다. 경로 규칙(절대경로 또는 저장소 밖 루트 + 상대경로)을 정해야 한다(H1과 연동).
  - (d) `video_id`가 "프로젝트 안에서 유일"인데 montage는 다른 프로젝트 영상도 섞을 수 있다. `<프로젝트>/<영상ID>` 형태로 전체 유일하게.
  - (e) 다른 프로젝트 담당이 부담스럽지 않도록 **최소 버전 예시**(id, start, end, reason, rights_ref만)를 따로 보여주면 brief의 "시작~끝 시간, 한 줄 이유"와 맞는다.
  - 시간 표기 불일치와 잘못된 `...` 줄은 직접 수정함(아래).
- **M5. 사용자 질문 4번이 두 질문** (spec 14절): "시범 프로젝트 선택"(A/B)과 "원본 보관 위치"(선택지 없음)가 섞였고, 추천 후보가 "강의 또는 책 해설" 둘이라 모호하다. 제안: 질문을 5번 항목으로 분리해 각각 2~3개 선택지 + 추천 1개(예: 시범은 완성 영상이 먼저 나오는 프로젝트 하나, 보관은 사용자 PC 폴더). H1의 "실행 장소"도 같은 형식으로 추가.

### 낮음
- **L1. 출처 없는 서술**: spec 11절 "할당량 태평양 시간 자정 초기화"는 리서치에 없는 내용이었다(제3자라고 적혀 있었음). 출처 표기를 정정함.
- **L2. 과한 일반화**: spec 14절 3번 근거 1 "같은 채널끼리만 가능"은 리서치(2023 기사)가 말한 범위를 넘어섰다. 표현 완화함. 14절 1번 A의 "심사 없이 시작 가능"도 "비공개 업로드로"라는 단서를 붙임.
- **L3. 쉬운 설명 부족** (style-guide "풀어서, 일상과 엮어"): spec은 개발자용 용어(dedup_key, 어댑터, SHA-256)가 많다. 사용자는 14절만 봐도 되지만, 문서 맨 위에 "쉬운 요약" 5줄(예: 우리 영상을 하이라이트처럼 잘라 올리는 일, 올리기 전 "택배 발송 전 확인"처럼 내가 승인, 같은 걸 두 번 안 보내는 장치 등)을 두기를 권장.
- **L4. 문서 관계**: 로드맵 1-9 실측 결과를 `youtube-upload` 스킬에 반영할 책임자는 총괄로 정해져 있으나 완료 기준(roadmap 1단계)에 "스킬 수정 반영"이 없다. 한 줄 추가 권장.
- **L5.** research-shorts.md는 출처·충돌·한계 표기가 충실해 수정 없음. 공식 도메인 접속 불가 한계가 있으니 구현 전 재조사 필요(이미 명시됨).
