## 한 줄 요약

"내가 관심 있는 입찰 공고만 골라서, 텔레그램으로 바로 알려주는" 작은 서비스를 먼저 내가 쓰고, 잘 되면 지인 업체에 싸게 판다. 데이터 원가는 0원이고, 처음부터 계정별로 조건을 따로 저장해서 나중에 판매할 때 다시 갈아엎지 않는다.

## 1. 목표

| 단계 | 목표 | 성공 모습 |
|---|---|---|
| 1단계 | 나 혼자 쓰면서 고도화 | 매일 내 조건에 맞는 공고가 텔레그램으로 오고, 놓친 공고가 없다 |
| 2단계 | 지인 업체 3~5곳에 저가 판매(파일럿) | 지인이 직접 조건을 넣고 알림을 받으며, 월 이용료를 낼 의향이 있다 |

비유하자면, 1단계는 "내 집 우편함에 내 우편물만 오게 하는 것"이고 2단계는 "같은 건물 이웃들 우편함도 각자 따로 달아주는 것"이다. 우편함(계정)은 처음부터 여러 개 달 수 있게 만든다.

## 2. 대상 사용자

| 구분 | 누구 | 원하는 것 |
|---|---|---|
| 1차 | 나 | 내 업종 공고를 놓치지 않기 |
| 2차 | 지인 업체(소규모, 입찰 참여 경험 있거나 시작하려는 곳) | 비싼 입찰정보 서비스(월 2만~3만 원대)보다 싸고 필요한 것만 있는 알림 |

## 3. 핵심 기능

### MVP (1~2주, 1단계)

| 기능 | 설명 | 비고 |
|---|---|---|
| 공고 수집기 | 입찰공고 API를 주기적으로 호출해 SQLite에 쌓는다 | 목록 오퍼레이션 중심, 증분 수집 |
| 계정별 관심 조건 | 계정마다 키워드·제외어·지역·금액 등을 따로 저장 | 처음부터 멀티 계정 구조 |
| 맞춤 공고 알림 | 새 공고가 조건에 맞으면 알림 | 텔레그램 기본, 채널은 교체 가능 |
| 중복 방지 | 같은 공고(공고번호+차수)는 한 계정에 한 번만 알림 | 정정공고는 별도 처리(아래 참고) |
| 간단한 웹 화면 | 내 조건 편집, 최근 공고 목록, 알림 내역 | 읽기·조건 편집 위주 |

### 이후(우선순위 순)

| 순번 | 기능 | 설명 |
|---|---|---|
| 1 | 마감 임박 정리 | 마감 3일 이내 공고를 하루 한 번 요약 |
| 2 | 관심 공고 저장·일정 캘린더 | 투찰 일정 관리 |
| 3 | 낙찰률 통계 | 낙찰정보 API로 업종·기관별 낙찰가율 참고 통계 (참고용 표시 필수) |
| 4 | 사전규격 알림 | 공고 전 단계 정보 |
| 5 | 이메일·카카오 채널 | 알림 채널 추가 |
| 6 | 결제·요금제 | 2단계 판매 시 |

## 5. 기술 선택안

| 영역 | 선택 | 이유 |
|---|---|---|
| 수집기 | Python | 재료가 풍부하고 단순 |
| DB | SQLite | 서버 불필요, 수십 계정까지 충분 [가정]. 커지면 Postgres로 이전 |
| 웹 | 가벼운 Python 웹 프레임워크(FastAPI 또는 Flask) + 단순 템플릿 | 1주 안에 만들 수 있는 크기 |
| 스케줄링 | 서버의 cron(또는 systemd timer)이 수집 스크립트를 주기 실행 | 별도 큐 시스템 없이 시작 |
| 비밀값 | `.env` (서비스키, 텔레그램 봇 토큰). 저장소에 커밋 금지(.gitignore) | 보안 기본 |
| 호스팅 | 소형 VPS 1대 [가정] | 월 5천~3만 원 수준(research 추정) |
| 알림 | 채널 추상화(아래) | 카카오·이메일을 나중에 끼우기 쉽게 |

### 스케줄링

| 작업 | 주기 | 내용 |
|---|---|---|
| 신규 공고 수집 | 30분마다 [가정] (업무시간 08~19시는 30분, 그 외 2시간으로 줄여도 됨) | 마지막 수집 시각 이후 등록분만 요청 |
| 알림 발송 | 수집 직후 | 매칭된 새 공고 |
| 마감 임박 요약 | 매일 아침 1회 | 이후 기능 |
| 낙찰정보 수집 | 매일 1회(새벽) | 이후 기능 |

### 중복 제거

| 항목 | 규칙 |
|---|---|
| 공고 고유 키 | `공고번호 + 차수` (예: 20261100123-00) |
| 저장 방식 | 키가 이미 있으면 덮어쓰기(upsert). 내용이 바뀌었으면 `변경됨` 표시 |
| 알림 중복 | `알림 기록` 표에 (계정, 공고 키) 유일 제약(6장 notifications와 동일). 이미 보냈으면 안 보냄. 여러 조건에 걸려도 한 번만 보내고 걸린 조건은 함께 표시 |
| 정정·재공고 | 차수가 올라가면 새 공고로 보고 "정정" 라벨을 붙여 한 번 더 알림 [가정: 이 방식이 편할지는 사용 후 판단] |

### 트래픽 한도 대응 (research-market.md 수치 기준)

현황: 입찰공고정보서비스 개발계정 **일 1,000건**, 운영계정은 활용사례 등록 후 신청해 증량(수치 미확인). 낙찰·사전규격 한도는 **[미확인]**.

| 대응 | 내용 |
|---|---|
| 증분 수집 | 매번 전체가 아니라 "마지막 수집 이후 등록분"만 요청. 한 페이지를 크게(100건 안팎) 받아 호출 수를 줄임 |
| 호출 예산 계산 | 4개 공고 종류(물품·공사·용역·외자) x 하루 48회 = 약 192회 + 페이지 추가분. 1,000건 안에 들어옴 [가정: 새 공고가 한 페이지에 담기는 경우] |
| 일일 카운터 | 호출마다 DB에 횟수 기록. 800건(80%) 넘으면 수집 간격을 늘리고 나에게 경고 알림 |
| 초기 백필 분리 | 과거 데이터 채우기는 하루 예산을 나눠 며칠에 걸쳐 진행. 처음엔 최근 며칠 치만 |
| 오류 처리 | 429·타임아웃은 재시도 간격을 늘려서(백오프) 재시도, 당일 한도 초과 시 다음 날 이어서 |
| 사용자 수와 무관 | 수집은 서비스 전체에서 한 번만 하고 매칭은 DB 안에서 한다. 사용자가 늘어도 API 호출은 안 늘어난다 |
| 운영계정 전환 | 1단계 중에 활용사례를 등록해 신청. 판매 전 필수 선결 과제 |
| 오퍼레이션 확인 | 공사·물품·외자의 정확한 오퍼레이션명·필드는 **[미확인]**. 개발 시작 때 data.go.kr에서 확인하고 g2b-bid-data 스킬도 고친다 |

## 6. 데이터 모델 (멀티 계정)

의사 스키마. 실제 DDL은 developer 단계에서 작성.

| 표 | 주요 칸 | 설명 |
|---|---|---|
| accounts | id, email, password_hash, display_name, status(active/paused), created_at | 이용자 계정 |
| channels | id, account_id, type(telegram/email/...), address(예: chat id), enabled | 계정별 알림 채널 |
| conditions | id, account_id, name, enabled, 조건 JSON(아래), created_at | 계정별 관심 조건. 한 계정이 여러 개 가능 |
| bids | bid_no, bid_ord(차수), 종류, 제목, 공고기관, 수요기관, 지역, 업종, 물품분류, 추정가격/기초금액, 공고일시, 입찰마감, 개찰일시, 원문URL, raw_json, updated_at | 수집한 공고. 기본키 (bid_no, bid_ord) |
| notifications | id, account_id, condition_id, bid_no, bid_ord, channel_id, status(sent/failed), sent_at | 알림 기록. (account_id, bid_no, bid_ord) 유일 |
| api_usage | date, service, call_count | 일일 호출 카운터 |
| settings | key, value | 수집 마지막 시각 등 |

핵심은 **공고(bids)는 모두가 같이 쓰고, 조건(conditions)과 알림(notifications)만 계정별로 나뉜다**는 점이다. 이렇게 하면 한 번 수집해서 여러 업체가 재활용한다(스타일 선호: 하나 만들어 여러 곳에 재활용).

### 조건 항목 정의

모든 항목은 비워두면 "제한 없음". 업종·품목·지역은 미정이므로 값은 사용자가 정하고, 구조만 만들어 둔다.

| 항목 | 타입 | 예시 | 동작 |
|---|---|---|---|
| 이름 | 문자 | "내 본업 공고" | 알림에 표시 |
| 공고 종류 | 목록(복수) | 물품 / 공사 / 용역 / 외자 | 수집 종류와 일치 |
| 키워드(포함) | 목록 | ["CCTV", "영상"] | 제목에 하나라도 있으면(OR) 통과. 모드 옵션: 전부(AND) |
| 제외어 | 목록 | ["유지보수"] | 하나라도 있으면 탈락 |
| 업종코드 | 목록 | 참가자격 업종 코드 | 공고의 제한 업종과 일치 |
| 물품분류 | 목록 | 물품분류번호 / 세부품명번호 | 물품 공고에 적용 |
| 지역 | 목록 | 시도 단위(서울, 경기 ...) | 수요기관 지역 또는 참가 제한 지역 기준 |
| 금액 범위 | 최소/최대 | 5천만~3억 | 추정가격(없으면 기초금액) 기준 |
| 공고기관 | 목록 | 특정 기관명 | 포함/제외 둘 다 가능 |
| 입찰 방식 | 목록 | 일반경쟁 / 제한경쟁 / 수의 등 | 선택 |
| 마감까지 최소 일수 | 숫자 | 2 | 마감 임박해서 못 하는 공고 제외 |
| 알림 시간대 | 시간 범위 | 08~21시 | 그 밖엔 모아서 다음 시간대에 발송 |
| 알림 채널 | 목록 | 텔레그램 | 계정의 채널 중 선택 |

조건 저장 예시(JSON 의사코드):

```
{ "kinds": ["물품"],
  "keywords_any": ["CCTV","영상"],
  "exclude": ["유지보수"],
  "regions": ["경기","서울"],
  "amount": {"min": 50000000, "max": 300000000},
  "min_days_to_deadline": 2 }
```

매칭 순서: 종류 -> 제외어 -> 금액 -> 지역 -> 업종/분류 -> 키워드. 싼 검사를 먼저 해서 빠르게 걸러낸다.

## 7. 알림 채널 추상화

| 구성 | 내용 |
|---|---|
| 공통 약속(인터페이스) | `send(수신주소, 메시지)` 하나. 결과는 성공/실패+사유 |
| 1순위 구현 | 텔레그램 봇. 계정이 봇에게 말을 걸면 chat id를 연결 |
| 나중에 추가 | 이메일, 카카오 알림톡(건당 과금, 단가 미확인) |
| 메시지 틀 | 제목, 기관, 금액, 마감, 링크, "어떤 조건에 걸렸는지" |
| 실패 처리 | 3회 재시도 후 실패 기록. 한 채널 실패가 다른 알림을 막지 않음 |

| 공고 원문의 담당자 연락처 등 | 공고에 담당자 이름·전화가 있으면 **저장하지 않거나 화면에 안 보여줌**(필요 시 원문 링크로 안내) | - |
| 비밀값 | 서비스키·봇 토큰은 `.env`, 로그에 찍지 않음 | - |
| 기타 | HTTPS, 로그인 시도 제한, DB 파일 정기 백업, 탈퇴 시 계정·조건·알림 기록 삭제 | - |

## 9. 낙찰가 예측·통계 표시 원칙

- 낙찰가율 통계·예측은 **참고용**이며 낙찰·수익을 보장하지 않는다. 화면 해당 부분에 항상 문구를 넣는다. 예: "과거 데이터 기반 참고용 통계이며 실제 낙찰을 보장하지 않습니다. 투찰 판단과 책임은 이용자에게 있습니다."
- 투찰 금액을 "추천"하는 표현은 쓰지 않는다. "과거 평균 낙찰률 OO%" 같은 사실 중심으로 보여 준다.
- 원문 링크를 항상 달아, 최종 확인은 나라장터에서 하게 한다. 우리 알림은 누락·지연이 있을 수 있음을 약관에 적는다.
- 이 기능은 MVP 이후. 1단계 사용 중 필요성 판단.

## 10. 비용·법적 위험 (한 칸 요약)

| 구분 | 1단계 | 2단계 |
|---|---|---|

## 12. 가격은 어떻게?

research-market.md의 안 A/B/C 중 정해지는 대로 2단계에서 적용. 현재 추천은 C(지인 파일럿 3개월 무료 후 월 14,900원) -> B(Basic 9,900 / Plus 19,900)다. 다만 이비드코리아 12개월 환산이 월 약 1.6만 원이라 가격만으로는 차별이 약하므로 "텔레그램 알림 + 낙찰률 통계" 같은 좁은 기능이 포인트다.
