## 단계별 상세

### D0. 준비·확인 (S1)

| 항목 | 내용 |
|---|---|
| 할 일 | (1) data.go.kr 서비스키 발급 (아래 단계별 안내) (2) 텔레그램 봇 만들기(BotFather) (3) spec-v3 16장 미확인 10개 항목 확인 (4) 목록 응답의 실제 필드로 spec 11-1 허용 필드 후보 표 확정 (5) g2b-bid-data 스킬에 확정된 오퍼레이션 이름·조회기간 규칙 반영 (6) 조건 초안: 전 업종·전국이라 제외어 몇 개만 먼저 정하기 (7) 내 PC 운영체제 확인(스케줄러 선택용: Windows 작업 스케줄러 / macOS·Linux cron) |
| 담당 | 사용자(키 발급, 봇 만들기, PC 운영체제 알려주기) / 총괄 세션(curl로 참고문서·활용신청 화면·실제 응답 확인) / researcher(결과 정리·스킬 문서안) / skill-scout(텔레그램 연동 스킬 유무 확인) |
| 작업량 | 사용자 1~2시간 + 확인 약 1일(v2의 반나절에서 늘어남: 항목 2개 추가, 허용 필드 확정) |
| 완료 기준 | 서비스키가 `.env`에 있고 채팅·git에 없음 / 미확인 10개가 `outputs/d0-confirmed.md` 표로 채워짐(특히 numOfRows 최대, 트래픽 단위, 공공누리 유형, 증량·활용사례 등록 요건) / spec 11-1 허용 필드 표의 "확정" 칸이 채워지고 응답에 없는 후보는 삭제됨 / 7일 규칙이 낙찰·사전규격·개방표준에도 적용되는지 기록 / g2b-bid-data 스킬 수정안 반영 |

서비스키 발급 단계별 안내 (화면 문구는 사이트 개편으로 조금 다를 수 있음):

1. 브라우저 주소창에 data.go.kr을 입력해 연다. 공공데이터포털 첫 화면이 보인다.
2. 화면 오른쪽 위의 [로그인]을 누른다. 로그인 창이 열린다. (회원이 아니면 [회원가입]을 먼저 한다.)
3. 아이디와 비밀번호를 넣고 로그인한다. 오른쪽 위에 내 이름이 보이면 성공이다.
4. 상단 검색창에 "조달청 나라장터 입찰공고정보서비스"를 입력하고 검색한다. 검색 결과 목록이 나온다.
5. 결과에서 같은 이름의 오픈API 항목을 누른다. 상세 페이지가 열리고 개발계정 트래픽, 이용허락범위, 참고문서(첨부파일) 목록이 보인다.
6. 상세 페이지의 개발계정 트래픽·이용허락범위·심의 값을 메모한다. (D0 확인 항목 2·3번에 쓴다.)
7. 오른쪽의 [활용신청] 버튼을 누른다. 활용 목적을 적는 입력창이 나타난다.
8. 활용 목적에 "나라장터 입찰 공고 알림 서비스 개발"이라고 쓴다. 사실과 다르게 쓰지 않는다.
9. 이용약관 동의 칸을 체크한다.
10. [신청]을 누른다. 심의가 자동승인이라고 안내되어 있으므로 [직접 확인: 활용신청 심의 자동승인] 승인 상태로 바뀌는지 본다. 바로 안 바뀌면 잠시 뒤 다시 확인한다.
11. 오른쪽 위 [마이페이지]를 누른다. 내 정보 화면이 열린다.
12. 개발계정(활용 현황) 목록에서 방금 신청한 서비스 이름을 누른다. 일반 인증키가 Encoding / Decoding 두 종류로 보인다.
13. 인증키 한 가지를 복사한다. 어느 쪽 키(Encoding/Decoding)를 쓸지는 developer가 D1 첫날 시험 호출로 정하므로 두 가지 모두 복사해 둔다.
14. 프로젝트의 `.env` 파일을 열어 인증키를 붙여 넣고 저장한다. 채팅·메모·문서에는 붙이지 않는다.
15. 4~14단계를 낙찰정보서비스, 사전규격정보서비스, 공공데이터개방표준서비스에 대해 반복한다. 모두 무료이고 입찰공고정보서비스만 필수다. 인증키가 서비스마다 따로 나오면 `.env`에 이름을 구분해 넣는다.
16. 키가 바로 안 되면 기다린다. 활성화까지 몇 분~1시간 걸릴 수 있다 [추정].

텔레그램 봇 만들기 단계별 안내:

1. 텔레그램 앱 검색창에 "BotFather"를 입력한다. 검색 결과가 보인다.
2. 파란 체크 표시가 있는 공식 BotFather 계정을 누른다. 대화창이 열린다.
3. 대화창에 `/newbot`을 보낸다. 봇 이름을 물어보는 답이 온다.
4. 봇 이름(화면에 보이는 이름)을 보낸다. 봇 아이디를 물어보는 답이 온다.
5. 봇 아이디(끝이 bot으로 끝나는 이름)를 보낸다. 완료 메시지에 봇 토큰이 나온다.
6. 봇 토큰을 복사한다.
7. 프로젝트의 `.env`에 토큰을 붙여 넣고 저장한다. 채팅에는 붙이지 않는다.
8. 텔레그램 검색창에 방금 만든 봇 아이디를 입력해 봇을 연다. 빈 대화창이 열린다.
9. `/start`를 보낸다. 지금은 봇이 답하지 않는 것이 정상이다(답장 기능은 D2에서 만든다).

텔레그램 chat id 연결 방법(D2에서 구현, 계정마다 이용): 사용자가 봇에게 `/start`를 보내면 프로그램이 chat id를 받아 계정에 저장하고 "연결됐습니다"라고 답한다. 사용자가 주소창에 봇 토큰을 직접 넣는 방식은 토큰이 브라우저 기록에 남으므로 쓰지 않는다.

| 작업량 | 약 4일 |

D1 실측 직후 판단: (가) 호출량이 한도 안이면 그대로, (나) 부족하면 spec 6-6 대응 순서 적용, (다) 증량 신청 요건이 D0에서 가벼운 것으로 확인됐다면 이때 신청(아래 "증량 신청").

| 담당 | developer (텔레그램 스킬이 필요하면 skill-scout) |
| 작업량 | 약 4일 |
| 완료 기준 | 하루 2~3번 지정 시각에 묶음이 온다 / 마감 임박 공고가 묶음 맨 위에 마감 빠른 순으로 나온다 / 같은 공고가 두 번 오지 않음 / 테스트 계정 2개가 서로 다른 조건·발송 시각으로 각자 다른 묶음을 받는다 / 전 업종 조건에서도 건수 상한·요약 줄이 동작한다 |

D2 완료일이 **사용 시작일**이다. 이 날부터 한 달 뒤가 판매 결정 시점이다.

### VPS 이전 (D2 직후, 사용 시작일 직후, S1)

기본 시점은 D2 완료 직후(달력 약 2주차 말, 결정 "1~2주 뒤"에 해당). D1이 일찍 끝나 PC에서 며칠 이상 안정적으로 돌았다면 D2 중에도 가능하다. VPS 업체는 사용자가 고른다(월 약 5천~3만 원 [추정]).

| 항목 | 내용 |
|---|---|
| 담당 | 사용자(VPS 신청, 접속 정보 보관) + developer(설치·확인) |
| 작업량 | 0.5~1일 |
| 완료 기준 | VPS에서 이틀 연속 수집·발송이 돌고, 중복 알림·한도 초과·로그 키 노출이 없음 / PC 쪽 스케줄이 꺼져 있고 PC의 `.env` 사본이 삭제됨 |

이전 절차 (한 단계에 행동 하나, 위에서부터 차례로):

1. [PC] 수집·발송 스케줄을 끈다(작업 스케줄러 또는 cron 항목을 비활성화). 이후 실행 기록(collect_runs)에 새 줄이 더 늘지 않는다.
2. [PC] 지금 돌고 있는 작업이 끝났는지 확인한다. 마지막 실행의 상태가 "성공" 또는 "완료"로 보인다.
3. [PC] 마지막 성공 시각(settings 표)을 기록해 둔다. 이전 뒤 이어받는 기준이 된다.
4. [PC] SQLite 백업 기능으로 백업 파일을 만든다. 파일을 그냥 복사하지 않는다(WAL 모드라 복사본이 깨질 수 있음). 백업 파일이 생기고 크기가 0이 아닌 것을 본다.
5. [VPS 업체 사이트] VPS를 신청한다. 접속 주소와 접속 방법이 안내된다.
6. [VPS] 접속해서 Python과 프로젝트 코드를 설치한다(git에서 받음). 프로그램 시험 실행이 오류 없이 시작된다.
7. [VPS] `.env`를 만들어 서비스키와 봇 토큰을 직접 붙여 넣는다. git이나 채팅으로 옮기지 않는다. (D0 확인 10번에서 키가 IP로 제한되지 않는지 이미 확인된 상태여야 한다.)
8. [VPS] 백업 파일을 복사해 DB로 연다. 공고 건수가 PC에서 센 건수와 같다.
9. [VPS] 수집을 한 번 수동 실행한다. collect_runs에 성공 줄이 생기고, 마지막 성공 시각 이후가 6일 이하 조각으로 따라잡힌다.
10. [VPS] 테스트 계정으로 묶음 발송을 한 번 실행한다. 텔레그램에 묶음이 오고, PC가 꺼져 있는데도 중복이 없다.
11. [VPS] 스케줄(cron)에 수집 30분마다와 발송 시각을 등록한다. 다음 정각에 자동 실행 기록이 생긴다.
12. [PC] 이틀 뒤 호출 카운터·알림·로그를 확인하고, 문제가 없으면 PC의 `.env` 사본과 서비스키 메모를 지운다. 지운 뒤에도 VPS에서 알림이 계속 온다.

주의: 같은 서비스키·봇 토큰을 PC와 VPS가 동시에 쓰면 한도가 이중으로 소모되고 알림이 두 번 간다. 1단계(PC 정지)를 반드시 먼저 한다. 문제가 생기면 PC 스케줄을 다시 켜고 VPS를 멈추는 순서로 되돌린다(데이터는 6일 조각으로 따라잡힘).

### 증량 신청 (별도, 판매 결정과 무관, D1~D3 사이)

결정: 판매 준비는 한 달 뒤에 정하지만 호출 한도 증량 신청은 일찍 한다. 증량 신청은 비용이 들지 않고 판매하지 않아도 필요할 수 있기 때문이다.

| 항목 | 내용 |
|---|---|
| 먼저 알아야 할 것 | D0 확인 7번: 승인 방식(자동인지 심사인지)·소요시간·증량 수치, 활용사례 등록에 필요한 것(웹 주소, 화면 캡처, 사업자 여부, 개인 사용도 가능한지). 모두 미확인이다 |
| 시점 규칙 | (1) 요건이 가벼움(공개 화면이 필요 없음) -> D1 실측 직후 신청 (2) 요건에 화면·웹 주소가 필요함 -> D3 완료 직후 신청, 그 전에 한도 부족이 보이면 spec 6-6 (1)~(4) 대응을 먼저 쓰고 최소 화면을 앞당길지 판단 (3) 개인 사용은 등록 불가로 확인됨 -> 판매 결정 이후로 미루고 대응책으로 버팀 |
| 담당 | 사용자(신청 화면 입력) + developer(화면 캡처·설명) |
| 작업량 | 반나절 |
| 완료 기준 | 신청 결과(승인 방식·소요시간·늘어난 수치)를 spec 6-2에 기록 |

활용사례는 사실대로 적는다("나라장터 입찰 공고 알림 서비스, 현재 개인 사용"). 판매 계획을 확정된 것처럼 쓰지 않는다.

## 유출 시 대처 (서비스키 / 봇 토큰 각각, 한 단계에 행동 하나)

화면 문구는 사이트·앱 개편으로 다를 수 있고, 데이터포털의 재발급 기능 이름은 미확인이라 D0에서 실제 화면을 보고 이 절을 고친다.

서비스키가 로그·git·채팅에 노출되었을 때:

1. 수집·발송 스케줄을 끈다. 이후 호출이 멈춘다.
2. data.go.kr에 로그인해 [마이페이지]를 연다.
3. 개발계정(활용 현황) 목록에서 해당 서비스 이름을 누른다. 인증키가 보인다.
4. 인증키 재발급(또는 갱신) 버튼을 누른다. 새 키가 나온다. 재발급 버튼이 없으면 활용신청을 삭제하고 다시 신청해 새 키를 받는다 [추정, D0에서 확인].
5. 새 키를 복사해 `.env`의 옛 키를 바꾸고 저장한다.
6. 로그 파일·백업·git 이력에서 옛 키 앞부분을 검색한다. 나오면 해당 파일을 지운다(git에 올렸다면 키 재발급이 우선이고 이력 정리는 그다음이다).
7. 스케줄을 다시 켠다. 첫 호출이 정상 응답(오류 없음)으로 기록된다.

봇 토큰이 노출되었을 때:

1. 수집·발송 스케줄을 끈다.
2. 텔레그램에서 BotFather 대화창을 연다.
3. `/revoke`를 보낸다. 내 봇 목록이 나온다.
4. 해당 봇을 누른다. 새 토큰이 표시되고 옛 토큰은 쓸 수 없게 된다.
5. 새 토큰을 복사해 `.env`의 옛 토큰을 바꾸고 저장한다.
6. 로그·백업·git 이력에서 옛 토큰을 검색해 지운다.
7. 스케줄을 다시 켠다. 테스트 메시지가 도착한다.

| 증량 신청 요건이 개인 사용에 불리(공개 서비스 필요) | 증량이 늦어짐 | D0 7번 확인, D3 화면을 활용사례로 사용, 그 사이는 6-6 대응(1)~(4) |

| PC가 꺼지거나 절전 상태(이전 전 1~2주) | 수집·발송 지연 | 6일 조각 따라잡기로 데이터는 보존, 꺼진 동안의 묶음은 합쳐 발송, 이전 후 해소. 이전 기간 동안 PC 절전을 꺼 둔다 |
| VPS 이전 중 PC와 VPS가 동시에 돎 | 호출 이중 소모, 알림 중복 | 이전 절차 1단계에서 PC 먼저 정지, 실패 시 되돌리는 순서 명시 |
