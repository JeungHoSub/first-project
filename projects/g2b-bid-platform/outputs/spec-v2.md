## 한 줄 요약

"내가 관심 있는 입찰 공고를 30분마다 모아 두었다가, 하루 2~3번 텔레그램 한 통으로 묶어 알려 주는" 작은 서비스를 먼저 내가 쓰고, 잘 되면 지인 업체에 싸게 판다. 데이터는 공식 API에서 무료로 받는다(이용허락범위 "제한 없음"·무료 [직접 확인], 단 공공누리 유형·출처표시 의무는 판매 전 최종 확인). 처음부터 계정별로 조건을 따로 저장해, 판매할 때 구조를 다시 만들지 않는다.

비유하면, 30분마다 우편물을 우체국에서 가져와 분류해 두고(수집), 하루 2~3번 각자 우편함에 한 묶음으로 넣어 주는 것(다이제스트)이다. 급한 우편(마감 임박)은 묶음 맨 위에 올려 놓는다.

### 흐름

```
[30분마다 스케줄러] -> [수집기: 오퍼레이션 3종 호출] -> [DB에 공고 저장(중복 제거)]
                                                         |
                                            [매칭: 계정별 조건 vs 새 공고]
                                                         |
                                  [대기 목록(pending)에 쌓기: 일반 / 마감 임박 표시]
                                                         |
                           [정해진 발송 시각(하루 2~3번)] -> [묶음 메시지 만들기]
                                                         |
                                       [텔레그램 어댑터] -> 사용자
```

수집·매칭은 30분마다 돌고, 발송만 하루 2~3번이다. 수집을 줄이지 않는 이유는 마감 임박 판정과 정정공고 반영을 최신으로 유지하기 위해서다.

## 5. 묶음 알림(다이제스트) 설계

### 규칙

| 항목 | 규칙 |
|---|---|
| 발송 횟수 | 계정마다 하루 2~3번. 기본 08:30 / 12:30 / 17:00 [기본값, 설정에서 변경 가능] |
| 시간대 설정 | 계정 설정에서 시각 2~3개를 고른다. 1번이나 4번 이상은 막는다 |
| 묶음 맨 위 | "마감 임박" 구역. 마감까지 24시간 이내(기본값, 설정 가능)인 공고를 마감 빠른 순으로 |
| 그 아래 | 일반 구역. 조건 이름별로 나누고 마감 빠른 순 |
| 이미 마감 지난 공고 | 대기 목록에서 빼고 발송하지 않음 |
| 이전에 보낸 공고 | 마감이 가까워져도 다시 보내지 않음(중복 방지). 재알림은 이후 기능 |
| 정정공고 | 차수가 올라가면 "정정" 라벨. 원본을 아직 안 보냈다면 최신 차수만 보냄 |
| 건수 상한 | 한 묶음 최대 50건 [기본값, 설정 가능]. 넘으면 마감 임박을 먼저 채우고 나머지는 "외 N건"으로 표시 |
| 맨 윗줄 요약 | "이번 묶음 N건 (마감 임박 n건) / 물품 a, 용역 b, 공사 c" |
| 메시지 길이 | 텔레그램 한 메시지는 4,096자 한도 [추정, 일반적으로 알려진 값]. 넘으면 메시지를 나눠 보내고 마감 임박 구역은 첫 메시지에 둠 |
| 한 건 표기 | 제목, 기관, 금액, 마감 일시, 원문 링크, 걸린 조건 이름 |
| 전달 실패 | 3회 재시도 후 실패 기록. 다음 발송 시각에 실패분을 앞에 붙여 다시 시도 |

### 전 업종·전국이라 생기는 문제와 대응

전 업종·전국이면 조건이 사실상 "제한 없음"이라 묶음이 매우 길어질 수 있다. 하루 신규 공고 건수는 공식 통계를 못 찾았다(미확인). 실제 건수는 D1 첫날 totalCount로 잰다. 그동안의 안전장치는 위의 건수 상한(50건)과 맨 윗줄 요약이다. 쓰면서 제외어·키워드를 넣어 좁혀 간다.

### 대기 목록 상태

pending(발송 대기) -> sent(발송됨) / failed(실패 후 재시도 중) / expired(마감 지나 취소). 같은 (계정, 공고번호, 차수)는 한 번만 sent가 된다.

| 낙찰정보 | 1,000 | 〃 | 〃 | 〃 |
| 사전규격정보 | 1,000 | 〃 | 〃 | 〃 |
| 공공데이터개방표준 | 10,000 | 〃 | 〃 | 〃 |

- 운영계정: 활용사례를 등록하면 증가 신청 가능. 승인은 자동승인이라 빠를 가능성이 있다. 늘어나는 수치는 미확인.
- 조회기간: 2026-11-10부터 전체 오퍼레이션의 요청 조회기간이 1개월에서 7일로 줄었다. 한 번 호출로 7일을 넘는 기간은 조회할 수 없다.

### 6-3. 증분 수집 설계 (조회기간 7일 반영)

증분 수집 = 지난번 이후 새로 올라온 것만 가져오기.

| 항목 | 규칙 |
|---|---|
| 조회 구간 | 오퍼레이션별로 "마지막 성공 종료 시각 - 겹침 1시간"부터 "지금"까지 |
| 겹침 이유 | 등록 시각이 늦게 반영되는 공고를 놓치지 않기 위해. 겹친 만큼 같은 공고가 다시 오지만 (공고번호+차수) upsert로 중복이 사라진다 |
| 구간이 7일 초과일 때 | 내 PC가 꺼져 있었던 경우 등. 7일 이하 조각으로 잘라 오래된 것부터 차례로 따라잡기 |
| 기준 시각 종류 | 공고 게시일시 기준인지, 정정공고가 변경일시로도 조회되는지는 D0에서 확인(미확인). 정정을 놓치지 않는 방법이 핵심 |
| 완전성 검사 | 응답의 전체 건수(totalCount)와 실제로 받은 행 수를 비교, 다르면 해당 구간 다시 수집 |
| 마지막 성공 시각 저장 | 구간 전체를 끝까지 받았을 때만 갱신(중간 실패 시 이전 값 유지) |
| 시간 기준 | 한국 시간(KST). 하루 카운터 초기화 시각은 자정으로 추정, D0에서 확인 |

### 6-4. 백필(과거 데이터 채우기) 설계

백필 = 과거 데이터를 한꺼번에 채우기. 7일 제한 때문에 "7일 조각 x 종류 3개 x 페이지 수"만큼 호출이 든다.

| 규칙 | 내용 |
|---|---|
| MVP 백필 범위 | 최근 7일치 1조각만. 미리보기("지난 7일 공고")에 필요한 만큼 |
| 호출 수 공식 | 백필 호출 수 = 3종 x 7일 조각 수 x 조각당 페이지 수 |
| 예산 | 정규 수집(아래 6-5)을 먼저 확보하고, 남는 호출에서 하루 최대 400회만 백필에 쓴다 |
| 낙찰률용 과거 데이터 | 낙찰정보 서비스는 한도가 따로(1,000)라 별도 예산으로 며칠에 걸쳐 진행 [추정] |

예시(조각당 페이지 수 P가 변수. 실제 값은 D1에서 측정): 28일 백필 = 3종 x 4조각 x P = 12P회. P=10이면 120회, P=30이면 360회, P=100이면 1,200회(하루 한도 초과, 여러 날로 분할).

### 6-5. 하루 호출량 계산 (M-4 해소)

전제: 개발계정 한도를 "하루 호출 횟수 1,000"으로 가정한다(단위는 미확인). 수집은 3종 x 하루 48회(30분마다).

- 기본 호출: 3 x 48 = 144회/일 [계산]
- 공식: 하루 호출 수 = 3 x 48 x 올림(n / R)
  - n = 30분 사이 종류별 신규 공고 수(미확인, 변수)
  - R = 한 페이지에 받는 행 수(numOfRows 최대값 미확인, 변수)

| n (종류별 30분 신규) | R=10일 때 | R=100일 때 |
|---|---|---|
| 10건 | 144회 | 144회 |
| 50건 | 720회 | 144회 |
| 100건 | 1,440회 (한도 초과) | 144회 |
| 300건 | 4,320회 (한도 초과) | 432회 |

(모두 [계산]. n은 평균 가정이라 오전 몰림 시간대는 더 클 수 있음)

여기에 정정·갱신 확인용 여유 20~30%를 더해 본다. 따라서 R이 작으면 개발계정으로는 부족하고, R이 100 이상이면 대부분 충분하다. 이 판정은 D1 첫날에 n과 R을 재면 바로 나온다.

야간(예: 22시~06시)은 신규가 적을 것으로 보고 1시간 간격으로 줄이면 기본 호출을 더 줄일 수 있다 [추정].

### 6-6. 경고 임계치와 대응

| 단계 | 기준(하루 누적, 가정 한도 1,000) | 동작 |
|---|---|---|
| 주의 | 700회 도달 (70%) | 나에게 텔레그램 경고 1회. 백필 중단 |
| 위험 | 900회 도달 (90%) | 수집 간격 60분으로 자동 확대, 경고 1회 |
| 중단 | 1,000회 근접 (정확한 한도 직전) | 호출 중단, 다음 날 초기화 후 7일 이하 조각으로 따라잡기 |

- 카운터는 서비스 단위와 오퍼레이션 단위로 모두 기록한다(한도가 오퍼레이션별로 다를 수 있다는 사례 때문 [검색 요약]).
- 한도가 실제로 모자라면 대응 순서: (1) 페이지 크기 확대, (2) 야간 간격 확대, (3) 운영계정 증량 신청(D3 완료 직후), (4) 개방표준서비스(일 10,000)를 보조 수집원으로 사용 검토, (5) 수집 주기를 60분으로 완화.
- 고객이 늘어도 호출 수는 안 늘어난다. 수집은 한 번만 하고 매칭은 DB 안에서 하기 때문이다.

## 11. 개인정보·보안

### 11-1. 공고 원문 저장 규칙 (H-1 해소)

방식: **허용 목록(allowlist)**. bids의 개별 칸에 쓰는 필드와 raw_json에 남길 필드를 이름으로 지정하고, 나머지는 모두 버린다. 새로 생긴 필드는 자동으로 버려지므로, 금지 목록 방식(알려진 위험 필드만 지우기)보다 안전하다.

raw_json 저장 전에 반드시 제거하는 필드(공고 응답의 담당자 계열. 이름은 알려진 것 [추정]이며 D0에서 실제 응답으로 확인):

| 필드 이름(추정) | 내용 |
|---|---|
| `ntceInsttOfclNm` | 공고기관 담당자 이름 |
| `ntceInsttOfclTelNo` | 공고기관 담당자 전화번호 |
| `ntceInsttOfclEmailAdrs` | 공고기관 담당자 이메일 |
| `dmndInsttOfclNm`, `dmndInsttOfclTelNo`, `dmndInsttOfclEmailAdrs` | 수요기관 담당자 이름·전화·이메일 |
| `exctvNm` | 집행관(개인) 이름 |
| 이름에 `Ofcl`(담당자), `Tel`, `Email`, `Fax`가 들어가는 모든 필드 | 위 목록에 없는 변형 대비 |

추가 안전장치:

1. 저장 후 점검: bids 전체에서 전화번호·이메일 모양 문자열을 정규식으로 찾아 0건인지 확인하는 점검을 D1 완료 기준과 D4 검수에 넣는다.
2. 이미 저장된 데이터 점검: DB 백업과 운영자(나) 열람에도 적용되므로 "화면에 안 보임"만으로는 부족하다. 저장 단계에서 제거한다.
3. 담당자 연락이 필요하면 원문 링크로 안내한다.

### 11-2. 비밀값 노출 방지 (M-1 해소)

data.go.kr API는 서비스키를 주소(URL)에 붙여 보내므로, 오류 로그에 주소가 통째로 찍히기 쉽다. 텔레그램 봇 토큰도 주소에 들어간다.

| 대책 | 내용 |
|---|---|
| 로그 마스킹 | 모든 로그·예외 메시지에서 `serviceKey=` 뒤 값과 `bot<토큰>` 부분을 `***`로 바꾸는 필터를 공통으로 적용 |
| 주소 통째 출력 금지 | 로그에는 오퍼레이션 이름과 조회 구간만 남기고 완성된 주소는 남기지 않음 |
| 라이브러리 로그 | HTTP 라이브러리의 상세(디버그) 로그를 꺼 둠 |
| 검사 | 로그 파일에서 키 앞부분을 검색해 0건인지 D1 완료 기준·D4 검수에서 확인 |
| 커밋 방지 | `.env`는 `.gitignore`, 저장소에는 `.env.example`(빈 값)만. 서비스키·토큰은 채팅에 붙이지 않는다 |
| 유출 시 | 1) 키를 재발급하거나 봇 토큰을 BotFather에서 재발급 2) `.env` 교체 3) 로그·백업에서 노출 여부 확인 4) 수집기 재시작 (구체 화면 단계는 D0 안내서에서 정리) |

## 14. 가격 (VAT 포함, 월 환산 기준)

| 요금제 | 가격(VAT 포함) | 포함 기능(안) |
|---|---|---|
| Basic | 9,900원 | 맞춤 조건 N개, 하루 2~3번 묶음 텔레그램 알림, 마감 임박 구역 |
| Plus | 14,900원 이하 | Basic + 조건 개수 확대, 낙찰률 참고 통계, 관심 공고·마감 일정 (S1에서 만든 것만 포함) |

경쟁사 비교(research-market-v2 4장 [계산], 경쟁사 요금은 [검색 요약]이며 공식 페이지 미열람):

| 우리 가격 | 인포21C 1개월 33,000 대비 | 인포21C 12개월 27,500 대비 | 이비드 1개월 21,000 대비 | 이비드 12개월 약 16,333 대비 |
|---|---|---|---|---|
| Basic 9,900 | 70.0% 낮음 | 64.0% 낮음 | 52.9% 낮음 | 39.4% 낮음 |
| Plus 14,900 | 54.8% 낮음 | 45.8% 낮음 | 29.0% 낮음 | 8.8% 낮음 |

- 해석: 14,900원 이하면 이비드 12개월 환산보다도 낮아 "더 싼 값" 목표에 맞다. 다만 이비드 연 결제와의 차이는 8.8%로 작아 가격만으로는 차별이 약하고, 묶음 알림·낙찰률 같은 좁은 기능이 포인트다.
- 비드프로·지투비·키다리·비드큐 요금은 확인하지 못했으므로 "가장 싸다"고 홍보하지 않는다. "인포21C 대비 절반 이하" 정도의 확인된 비교만 쓴다.
- 파일럿: 무료 3개월 후 유료 전환. 손익분기(월 원가 3만 원 [추정], 공급가 기준): Basic 9,000원 x 4곳 = 36,000원 -> 4곳. Plus 14,900원은 공급가 약 13,545원이라 3곳 [계산].
- Plus 정확한 금액(14,900 / 12,900 등)은 판매 준비(D6)에서 확정한다.

## 17. 용어 풀이

| 용어 | 쉬운 설명 |
|---|---|
| 오퍼레이션 | API가 하는 일 한 가지. 예: "물품 공고 목록 달라" |
| 서비스키 | 공공데이터포털이 내 프로그램에 주는 출입증 번호. 남에게 보이면 안 됨 |
| 개발계정/운영계정 | 개발계정은 시험용 낮은 한도, 운영계정은 활용사례를 등록하고 받는 높은 한도 |
| 증분 수집 | 지난번 이후 새로 올라온 것만 가져오기 |
| 백필 | 과거 데이터를 거슬러 올라가며 채우기 |
| upsert | 있으면 고치고 없으면 새로 넣기. 같은 공고가 두 번 저장되지 않게 함 |
| 백오프 | 실패하면 기다렸다가 다시 시도하되 기다리는 시간을 점점 늘리는 방법 |
| 다이제스트 | 알림을 하루 2~3번 한 묶음으로 모아 보내는 방식 |
| cron | 정해진 시각에 프로그램을 자동으로 실행하는 서버 기능 |
| chat id | 텔레그램에서 "이 사람 대화방"을 가리키는 번호 |
| WAL | SQLite가 쓰는 동안에도 다른 프로그램이 읽을 수 있게 하는 모드 |
| 허용 목록 | 저장해도 되는 필드를 이름으로 정해 두고 나머지는 버리는 방식 |
