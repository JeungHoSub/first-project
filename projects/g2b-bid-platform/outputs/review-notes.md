## 2. 지적 사항

심각도: 높음(개발 전 수정) / 중간(문서 수정 권장) / 낮음(참고)

### 높음

**H-1. 개인정보: 담당자 연락처를 "저장 안 함"이라 했지만 raw_json이 그대로 저장한다 (spec 8장 vs 6장)**
- spec 8장은 공고 담당자 이름·전화를 저장하지 않거나 화면에 안 보이게 한다고 했다. 그런데 6장 bids 표에 `raw_json`(API 응답 원문)이 있어 담당자 필드가 그대로 DB에 남는다.
- 제안: raw_json을 저장하기 전에 담당자명·전화·이메일 계열 필드를 제거(또는 raw_json을 아예 빼고 필요한 칸만 저장)한다고 spec에 한 줄 추가. DB 백업·운영자 열람에도 해당되므로 "화면에 안 보여줌"만으로는 부족하다.

### 중간

**M-1. 서비스키 노출 경로 보강 (spec 5장·8장)**
- `.env` 보관과 로그 금지는 잘 적혀 있다. 다만 data.go.kr API는 서비스키를 주소(URL)에 붙여 보내서, 오류 로그나 예외 메시지에 주소가 통째로 찍히기 쉽다.
- 제안: "로그·오류 메시지에서 서비스키 가리기(마스킹)", `.env.example`만 커밋, 키 유출 시 재발급 절차를 spec에 한 줄씩 추가.

**M-2. 출처 표기 정의와 실제 조사 방식이 어긋남 (research-market.md 상단)**
- "[확인] = 출처에서 직접 확인"이라 했지만, 같은 문서에서 data.go.kr·경쟁사 사이트를 직접 열람하지 못하고 검색 요약만 봤다고 밝힌다. 따라서 [확인]이 붙은 핵심 수치(개발계정 일 1,000건, 인포21C 33,000원 등)도 원문 열람은 아니다.
- 제안: 정의를 "[확인] = 검색 결과 요약에서 확인(원문 미열람)"으로 바꾸고, 핵심 수치(1,000건/일, 가격)는 2차 출처임을 spec·roadmap에서도 한 번 상기. 운영계정 전환 전에 마이페이지에서 실제 한도 재확인(이미 사용자 확인 3번에 있음).

**M-3. 가격 "더 싸게" 근거가 문서 안에서 엇갈림 (research 한 줄 결론 vs (b) 해석, 안 B)**
- 한 줄 결론은 "월 1만~2만 원대면 더 싸게가 성립"이라 했는데, (b) 해석은 "월 1만 원대는 이비드코리아 수준이라 차별 약함"이라 한다. 또 안 B의 Plus 19,900원은 이비드 12개월 환산(월 약 16,300원)보다 비싸서, brief의 "기존 서비스보다 싼 값" 목표와 부분적으로 충돌한다. 안 C의 14,900원도 이비드 연 결제(약 16,300원)와 차이가 작다.
- 제안: 결론 문장을 "인포21C 대비로는 싸지만 이비드 대비 차별은 약하다"로 조정. 가격안에 VAT 포함 여부 명시(인포21C 33,000원은 VAT 포함인데 우리 가격은 표기 없음). 비교 기준(1개월 vs 12개월 환산)을 표에서 통일.

**M-4. 트래픽 한도 계산의 전제가 낙관적, 단위도 모호 (spec 5장, roadmap 단계 1)**
- "1,000건/일"이 호출 횟수인지 받은 행 수인지 research에 명시가 없고, spec·roadmap은 "호출 횟수"로 해석해 192회로 계산했다. 그런데 research는 "하루 수만 건 공고 수집엔 부족"이라고 쓴다. 두 문서가 서로 다른 단위로 읽힌다.
- 또 "새 공고가 한 페이지(100건)에 담긴다"는 가정은 30분 사이 신규 공고가 100건을 넘으면 깨진다(특히 용역·물품 오전 시간대, 정정공고 포함).
- 제안: (1) 한도 단위를 "호출 횟수 [미확인]"으로 명시, (2) 호출 예산을 "페이지 수 2~3배" 시나리오로 한 번 더 계산, (3) research에 있는 공공데이터개방표준서비스(일 10,000건 [확인])를 대안·보조 수집원으로 검토한다는 항목 추가. 이 서비스는 spec에서 언급이 없다.

**M-5. MVP 범위·일정 표현이 서로 다름 (spec 3장 vs roadmap)**
- roadmap은 단계 2에 "MVP 완성"이라 쓰고, 아래에서는 "MVP(단계 0~4)는 약 2주"라고 한다. spec MVP는 웹 화면(단계 3)까지 포함한다. 소요일 합계도 1~2+3+3+3~4+2 = 12~14일(집중일 기준)이라 "약 2주"는 빠듯하고, 실사용 1주는 별도다.
- 제안: "MVP 핵심(알림) = 단계 2, MVP 전체 = 단계 0~4"로 구분하고 달력 기준 약 2.5~3주(+실사용 1주)로 수정. spec 3장 "1~2주"도 맞춰 수정.

**M-6. "1단계/2단계"와 roadmap "단계 0~7"의 용어 충돌 (spec·roadmap)**
- spec 3장 "MVP (1~2주, 1단계)", spec 5장 "1단계 중에 활용사례를 등록"의 1단계는 brief의 사업 단계(내가 직접 사용)인데, roadmap의 "단계 1"은 수집기 개발이다. 운영계정 신청 시점도 spec(1단계 중)과 roadmap(단계 4 직후)이 달라 보인다.
- 제안: roadmap은 "S0~S7" 또는 "작업 단계"로 이름을 바꾸고, 운영계정 신청 시점을 한 가지로 통일(추천: MVP 알림 작동 직후, 활용사례 등록에 실제 화면이 필요할 수 있으므로).

**M-7. 지인 파일럿 일정과 가격안이 맞지 않음 (roadmap 단계 7, research 안 C)**
- 안 C는 3개월 무료 후 유료인데, 단계 7은 1~3개월이면서 완료 기준이 "유료 전환 의사 확인"이다. 무료 기간 안에는 실제 결제를 볼 수 없다.
- 제안: 단계 7을 "3~4개월"로 늘리거나, 완료 기준을 "유료 전환 의사 확인(구두)"로 분명히 하고 실결제 확인은 이후로 분리.

**M-8. 사용자 질문이 두 문서에 중복되고 개수가 많음 (spec 마지막 표 9개, roadmap 6개)**
- 호스팅(spec 8 = roadmap 4), 업종·품목·지역(spec 1~3 = roadmap 1)이 중복이고 번호도 달라 답하기 헷갈린다. 사용자는 review/QUEUE.md만 본다.
- 선택지와 추천은 각 질문마다 잘 붙어 있어 형식은 좋다. 제안: 개발 시작 전 꼭 필요한 것 4개(업종·품목·지역 / 서비스키 발급 / 조사용 네트워크 허용 / 개발 시작 시점)만 QUEUE에 올리고, 나머지(가격안, 호스팅, 판매 시점 등)는 "나중에 정해도 됨"으로 분리. roadmap의 질문은 spec을 가리키는 방식으로 줄이기.

### 낮음

**L-1. 용어가 어려움 (스타일: 풀어서 쉽게)**
- spec 1장의 우편함 비유는 좋다. 그러나 증분 수집, upsert, 백오프, chat id, cron, 백필 같은 말은 처음 나올 때 설명이 없다. 사용자 질문 표는 대체로 쉽지만 spec 본문은 개발자용에 가깝다.
- 제안: 문서 끝에 "용어 풀이" 5~8줄 추가(예: 증분 수집 = 지난번 이후 새로 올라온 것만 가져오기).

**L-2. 사업자·상업 이용 확인 전 "데이터 원가 0원" 단정 (spec 한 줄 요약)**
- research에서 상업 이용·공공누리 유형이 미확인인데 요약은 "원가는 0원"이라 단정한다. 문서 안에 위험은 충분히 적혀 있으니 요약 문장에 "(이용 조건 확인 전)" 정도만 붙이면 된다.

**L-3. 기타 참고**
- SQLite에 수집기(쓰기)와 웹(읽기·조건 편집)이 동시에 접근한다. WAL 모드 사용을 개발 단계에서 확인.
- 알림에 여러 조건이 걸릴 때 notifications.condition_id는 첫 번째 조건만 담게 된다. 표시용 조건 목록은 별도 칸 또는 JSON으로(아래 직접 수정과 연결).
- 서비스 종류별 개발계정 한도는 오퍼레이션별로 다를 수 있다는 개인 사례(research (a))를 호출 카운터 설계에 반영(service 단위 집계는 이미 api_usage에 있어 대체로 충족).
- 개인정보처리방침은 판매(단계 6) 전에 쓰게 되어 있으나, 지인에게 계정을 주는 파일럿 시작 시점에 이메일·chat id를 수집하므로 단계 7 시작 전 반드시 완료되어 있어야 한다(현재 일정상 충족).

## 3. 통과 항목 요약

- 사실/추정 구분: research는 [확인]/[추정]/[미확인]을 일관되게 쓰고 한계를 먼저 밝혔다(정의 문제는 M-2). spec·roadmap도 [가정]/[미확인]을 달았다.
- 수치 일관성: 개발계정 일 1,000건, 낙찰·사전규격 한도 [미확인], 서버 월 5천~3만 원, 결제 수수료 약 3%, 원가 월 3만 원, 지인 3~5곳, 가격 9,900/19,900/14,900은 세 문서가 일치. 계산 확인: 인포21C 12개월 330,000/12 = 27,500, 이비드 196,000/12 = 약 16,300, 9,900/33,000 = 30%, 손익분기 30,000/9,900 = 약 3.03 -> 4곳.
- 보안·개인정보: 서비스키·봇 토큰 `.env`, 비밀번호 해시, 조건 비공개, 사업자번호 MVP 미수집, 카드번호 PG 위임, 탈퇴 시 삭제, 크롤링 금지. 모두 skill 지침과 부합.
- 낙찰가 참고용 고지: spec 9장에 문구 예시, "추천" 표현 금지, 원문 링크, 누락 면책. roadmap 단계 5·6 완료 기준에 반영. 통과.
- 법적 판단은 "일반 정보, 전문가 확인 필요"로 일관되게 한정.

## 4. 직접 수정한 내용 (사소한 수치·불일치)

1. research-market.md 안 B 근거: "40% 이상 낮음" -> "약 40% 낮음(19,900원 기준 39.7%)" (19,900/33,000 계산 결과와 불일치)
2. spec.md 중복 제거 표 "알림 중복": 유일 제약을 (계정, 조건, 공고 키) -> (계정, 공고 키)로 수정하고 여러 조건이 걸려도 한 번만 보내 조건을 함께 표시한다고 적음. 근거: spec 3장 "한 계정에 한 번만"과 6장 notifications 유일 제약이 이미 (계정, 공고 키)라서 문서 내 불일치 해소.
