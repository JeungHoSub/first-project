## 한 줄 요약

"내가 관심 있는 입찰 공고를 30분마다 모아 두었다가, 하루 2~3번 텔레그램 한 통으로 묶어 알려 주는" 작은 서비스를 먼저 내가 쓰고, 한 달 써 본 뒤 잘 되면 지인 업체에 싸게 판다. 데이터는 공식 API에서 무료로 받는다(이용허락범위 "제한 없음"·무료 [직접 확인], 단 공공누리 유형·출처표시 의무는 판매 전 최종 확인). 처음부터 계정별로 조건을 따로 저장해, 판매할 때 구조를 다시 만들지 않는다.

비유하면, 30분마다 우편물을 우체국에서 가져와 분류해 두고(수집), 하루 2~3번 각자 우편함에 한 묶음으로 넣어 주는 것(다이제스트)이다. 급한 우편(마감 임박)은 묶음 맨 위에 올려 놓는다. 우체국에 갈 때 "지난번에 가져온 시각보다 조금 앞부터" 달라고 하는 것이 겹침이고, 늦게 도착한 우편을 놓치지 않으려는 안전장치다. 이 겹침이 길수록 매번 받는 양이 늘어난다. 이 모든 일은 30분마다 "집배원이 한 바퀴 도는 것"(작업 스케줄러가 프로그램을 한 번 실행) 안에서 순서대로 끝난다. 집배원이 쉬지 않고 서 있는(상시 실행) 구조는 쓰지 않는다.

### 흐름 (30분마다 한 번 실행되는 "사이클" 하나)

```
[작업 스케줄러가 30분마다 run_cycle을 한 번 실행]
   |
   1. 텔레그램 새 메시지 확인: /start 연결 코드가 있으면 chat id 저장 + "연결됐습니다" 답장
   |
   2. 수집기: 오퍼레이션 3종 호출 -> DB에 공고 저장(중복 제거, 호출 한도 카운트)
   |
   3. 매칭: 계정별 조건 vs 새 공고 -> 대기 목록(pending)에 쌓기(일반 / 마감 임박 표시)
   |
   4. 발송: 지금 시각이 계정의 발송 시각이거나 이미 지났는데 못 보낸 묶음이 있으면
      묶음 메시지를 만들어 텔레그램으로 발송
   |
[프로그램 종료. 다음 사이클까지 아무것도 돌지 않음]
```

- 수집은 30분마다, 발송은 계정별 하루 2~3번만 일어난다. 수집을 줄이지 않는 이유는 마감 임박 판정과 정정공고 반영을 최신으로 유지하기 위해서다.
- 한 번 실행에 걸리는 시간이 30분을 넘으면 다음 실행과 겹친다. 그래서 (1) 작업 스케줄러 설정에서 "이미 실행 중이면 새로 시작하지 않음"을 고르고 (2) 프로그램 안에서도 잠금(실행 중 표시 파일)을 걸어 두 번 도는 것을 막는다. 둘 중 하나가 새도 나머지가 막는다.
- 1~4 중 앞 단계가 실패해도 뒤 단계는 시도한다(예: 수집 실패해도 이미 쌓인 pending은 발송 시각에 보낸다). 실패는 collect_runs와 경고로 남긴다.

## 5. 묶음 알림(다이제스트) 설계

### 규칙

| 항목 | 규칙 |
|---|---|
| 발송 횟수 | 계정마다 하루 2~3번. 기본 08:30 / 12:30 / 17:00 [기본값, 설정에서 변경 가능] |
| 시간대 설정 | 계정 설정에서 시각 2~3개를 **30분 단위(:00 또는 :30)**로 고른다. 1번이나 4번 이상은 막는다. 이유: 발송도 30분 사이클 안에서 일어나기 때문 |
| 실제 발송 시각 | 그 시각의 사이클에서 수집·매칭이 끝난 직후라 수 분 늦을 수 있다. 사이클이 한 번 빠졌으면 다음 사이클에서 "이미 지난 발송 시각"으로 보내므로 하루 횟수는 유지된다 |
| 묶음 맨 위 | "마감 임박" 구역. 마감까지 24시간 이내(기본값, 설정 가능)인 공고를 마감 빠른 순으로 |
| 그 아래 | 일반 구역. 조건 이름별로 나누고 마감 빠른 순 |
| 이미 마감 지난 공고 | 대기 목록에서 빼고 발송하지 않음 |
| 이전에 보낸 공고 | 마감이 가까워져도 다시 보내지 않음(중복 방지). 재알림은 이후 기능 |
| 백필로 받은 공고 | 과거 채우기로 받은 공고는 대기 목록에 넣지 않는다(미리보기·목록에는 보임). 과거 6일치가 한 묶음으로 쏟아지는 것을 막기 위함 |
| 정정공고 | 차수가 올라가면 "정정" 라벨. 원본을 아직 안 보냈다면 최신 차수만 보냄 |
| 건수 상한 | 한 묶음 최대 50건 [기본값, 설정 가능]. 넘으면 마감 임박을 먼저 채우고 나머지는 "외 N건"으로 표시 |
| 맨 윗줄 요약 | "이번 묶음 N건 (마감 임박 n건) / 물품 a, 용역 b, 공사 c" |
| 메시지 길이 | 텔레그램 한 메시지는 4,096자 한도 [추정, 일반적으로 알려진 값]. 넘으면 메시지를 나눠 보내고 마감 임박 구역은 첫 메시지에 둠 |
| 한 건 표기 | 제목, 기관, 금액, 마감 일시, 원문 링크, 걸린 조건 이름 |
| 전달 실패 | 3회 재시도 후 실패 기록. 다음 발송 시각에 실패분을 앞에 붙여 다시 시도 |
| PC가 꺼져 있던 경우 | 꺼진 동안 못 보낸 묶음은 켜진 뒤 첫 사이클에 한 번에 합쳐 보낸다(이미 마감 지난 것은 제외). VPS로 옮기면 거의 해당 없음 |

### 전 업종·전국이라 생기는 문제와 대응

전 업종·전국이면 조건이 사실상 "제한 없음"(훑어보기 조건)이라 묶음이 매우 길어질 수 있다. 하루 신규 공고 건수는 공식 통계를 못 찾았다(미확인). 실제 건수는 D1 첫날 totalCount로 잰다. 그동안의 안전장치는 위의 건수 상한(50건)과 맨 윗줄 요약이다. 쓰면서 제외어·키워드를 넣어 좁힌 조건으로 바꿔 간다.

### 대기 목록 상태

pending(발송 대기) -> sent(발송됨) / failed(실패 후 재시도 중) / expired(마감 지나 취소). 같은 (계정, 공고번호, 차수)는 한 번만 sent가 된다.

### 6-3. 증분 수집 설계 (조회기간 규칙 반영)

증분 수집 = 지난번 이후 새로 올라온 것만 가져오기.

| 항목 | 규칙 |
|---|---|
| 조회 구간 | 오퍼레이션별로 "마지막 성공 종료 시각 - 겹침"부터 "지금"까지. **겹침 기본 15분, 10~15분 범위에서 설정**(brief 결정). 한 번에 요청하는 구간은 약 40~45분 |
| 겹침 이유 | 등록 시각이 늦게 반영되는 공고를 놓치지 않기 위해. 겹친 만큼 같은 공고가 다시 오지만 (공고번호+차수) upsert로 중복이 사라진다 |
| 겹침을 줄인 대가 | 등록 반영이 겹침(10~15분)보다 더 늦은 공고는 놓칠 수 있다 [추정]. 그래서 D1에서 "공고일시와 처음 수집한 시각의 차이(등록 지연)"를 모두 기록하고, 하루 신규 중 지연이 15분을 넘는 건이 있는지 본다. 있으면 겹침을 늘리거나 하루 1회 넓은 재확인(아래)을 넣는다 |
| 넓은 재확인의 비용 (A-7) | 최근 24시간 재조회 = 하루 3 x 올림(48n / R)회 [계산]. **6-5 표와 여유 30%에 포함되어 있지 않다.** 예: R=100, n=100이면 144회 추가(정규 288 -> 432). R=100, n=10이면 15회, R=10, n=10이면 144회. 상한 근처(R=100, n=266)에서는 정규 576 + 재확인 384 = 960회라 위험 단계(900)를 넘으므로 **n 상한 근처에서는 재확인을 켜지 못한다**. 켤지는 D1 실측 n·R로 계산해 정한다 |
| 구간이 6일 초과일 때 | 내 PC가 꺼져 있었던 경우 등. 6일 이하 조각으로 잘라 오래된 것부터 차례로 따라잡기 |

| 완전성 검사 | 응답의 전체 건수(totalCount)와 실제로 받은 행 수를 비교, 다르면 해당 구간 다시 수집. (같은 구간 안의 누락만 잡는다. 늦게 등록된 공고는 위 등록 지연 기록으로 따로 본다) |

### 6-4. 백필(과거 데이터 채우기) 설계 (A-1 해소)

백필 = 과거 데이터를 한꺼번에 채우기. 조회기간 제한 때문에 "6일 조각 x 종류 3개 x 페이지 수"만큼 호출이 든다.

**호출 수 공식 (모두 [계산]):**

- 6일 = 30분 구간 288개. 한 종류의 6일치 행 수 = 288 x n (n = 30분 사이 종류별 신규, 미확인 변수). 백필은 겹침이 없다.
- 한 종류의 조각당 쪽 수 **P = 올림(288 x n / R)** (R = 한 페이지 행 수, 미확인 변수)
- **6일 1조각 백필 호출 수 = 3 x P** (물품·용역·공사)
- 하루 백필 예산 **B = 최소(400, 700 - 그날 정규 호출 수)**. 700은 주의 단계, 400은 백필 상한(6-6). B가 0 이하면 그날은 백필하지 않는다
- 걸리는 날 수 **N = 올림(3 x P / B)**

| R | n | P | 백필 호출 (3 x P) | 그날 정규 호출 (6-5 표, 겹침 15분) | 하루 예산 B | 걸리는 날 N |
|---|---|---|---|---|---|---|
| 100 | 10 | 29 | 87 | 144 | 400 | 1일 |
| 100 | 50 | 144 | 432 | 144 | 400 | 2일 |
| 100 | 100 | 288 | 864 | 288 | 400 | 3일 |
| 100 | 300 | 864 | 2,592 | 720 | 0 (정규만으로 주의 단계) | 백필 불가 |
| 10 | 10 | 288 | 864 | 288 | 400 | 3일 |
| 10 | 50 | 1,440 | 4,320 | 1,152 | 0 (정규가 한도 초과) | 백필 불가 |

(P 계산 예: R=100, n=10이면 288 x 10 / 100 = 28.8 -> 29쪽. R=10, n=50이면 288 x 50 / 10 = 1,440쪽. v3의 "6일 1조각 = P=10/30/100" 예시는 R·n에서 P가 정해진다는 점을 놓친 낙관치였다. 정규 호출 수에는 여유 30%를 넣지 않았다.)

| 규칙 | 내용 |
|---|---|
| MVP 백필 범위 | 최근 6일치 1조각만(D0에서 7일 가능 확인 시 7일). 미리보기에 필요한 만큼. **한 번에 다 못 받으면 며칠에 나눠 받는다** |
| 받는 순서 | 최근 것부터 거꾸로. 미리보기와 목록에 가까운 날이 먼저 채워지고, 중간에 멈춰도 쓸 만하다 |
| 나눠 받는 법 | 진행 위치(어디까지 받았는지)를 settings에 저장하고, 매 사이클 정규 수집이 끝난 뒤 예산 B가 남아 있으면 이어서 받는다. 하루 B를 다 쓰면 다음 날 이어서 |
| 예산 | 정규 수집(6-5)을 먼저 확보한다. 정규 수집이 700회에 가까운 날은 백필하지 않는다. 주의 단계(700)에 도달하면 백필 중단 |
| 백필 불가인 칸의 대응 | 정규만으로 주의 단계이거나 한도를 넘는 칸이다. 먼저 6-6의 대응(쪽 크기, 겹침 10분, 증량 신청)으로 정규 호출을 줄이는 것이 우선이고, 백필은 그 뒤로 미룬다. 그동안 미리보기·목록은 "수집을 시작한 날부터 쌓인 범위"만 보여 준다 |
| 알림 | 백필 공고는 알림 대상이 아니다(5장). bids에 `from_backfill` 표시 |
| 낙찰률용 과거 데이터 | 낙찰정보 서비스는 한도가 따로(1,000)라 별도 예산으로 며칠에 걸쳐 진행 [추정]. 조회기간 규칙이 같은지는 D0 확인 9번 |
| 더 오래된 과거 | 28일 백필은 6일치의 약 4.7배 호출이다(조각 경계 때문에 약간 더). MVP 범위 밖이며 필요해지면 위 공식으로 다시 계산한다 |

### 6-5. 하루 호출량 계산 (겹침 포함)

전제: 개발계정 한도를 "하루 호출 횟수 1,000"으로 가정한다(단위는 미확인). 수집은 3종 x 하루 48회(30분마다).

- 기본 호출: 3 x 48 = 144회/일 [계산] (모든 호출이 1쪽으로 끝날 때)
- 매번 요청하는 구간 길이 = 30분 + 겹침. 그래서 한 번에 받을 행 수는 n이 아니라 (30 + 겹침) / 30 x n 이다.
  - 겹침 15분: 45/30 = 1.5배, 겹침 10분: 40/30 = 약 1.33배 [계산]
- 공식: **하루 호출 수 = 3 x 48 x 올림( (30 + 겹침) / 30 x n / R )**
  - n = 30분 사이 종류별 신규·수정 공고 수(미확인, 변수. 3종이 같다고 가정)
  - R = 한 페이지에 받는 행 수(numOfRows 최대값 미확인, 변수)

(모두 [계산]. n은 평균 가정이라 오전 몰림 시간대는 더 클 수 있음)

| R | n (종류별 30분 신규) | 겹침 없음(v2 표) | 겹침 10분 | **겹침 15분(기본)** | 겹침 1시간(v2 설계, 폐기) |
|---|---|---|---|---|---|
| 10 | 10건 | 144 | 288 | **288** | 432 |
| 10 | 50건 | 720 | 1,008 | **1,152** | 2,160 |
| 10 | 100건 | 1,440 | 2,016 | **2,160** | 4,320 |
| 10 | 300건 | 4,320 | 5,760 | **6,480** | 12,960 |
| 100 | 10건 | 144 | 144 | **144** | 144 |
| 100 | 50건 | 144 | 144 | **144** | 288 |
| 100 | 100건 | 144 | 288 | **288** | 432 |
| 100 | 300건 | 432 | 576 | **720** | 1,296 |

읽는 법: 겹침 1시간 열은 v2 설계를 그대로 계산한 값이다(R=100·n=300에서 1,296회로 한도 1,000 초과). 겹침을 15분으로 줄이면 같은 칸이 720회로 내려가고, 10분이면 576회다. R=10일 때는 n이 26건(위험 단계 900 기준, 아래 표)만 넘어도 한도에 가까워져 겹침 조정만으로는 해결되지 않는다(R 확인이 핵심).

여유 20~30%(정정·갱신 확인용)를 더하면 R=100, n=300, 겹침 15분은 720 x 1.2~1.3 = 864~936회라 위험 단계(900) 근처다. 즉 이 칸은 이미 수집 간격이 자동으로 60분이 되는 영역이다.

**n 상한 표 (A-2 해소). 겹침 15분, 여유 30% 포함 [계산].** 기준은 **위험 단계 900회**다. 위험 단계를 넘으면 수집 간격이 60분으로 임시 확대되기 때문에, 평소 30분을 유지하려면 하루 호출(여유 포함)이 900 안이어야 한다. 1,000 기준은 한도 자체를 다 쓰는 값이라 참고로만 둔다.

| R | **위험 900 기준(핵심)**: 허용 쪽 수 / 호출(여유 포함) / **n 상한** | 주의 700 기준: 쪽 수 / 호출(여유 포함) / n 상한 | 1,000 기준(참고): 쪽 수 / 호출(여유 포함) / n 상한 |
|---|---|---|---|
| 10 | 4쪽 / 576 (749) / **26건** | 3쪽 / 432 (562) / 20건 | 5쪽 / 720 (936) / 33건 |
| 50 | 4쪽 / 576 (749) / **133건** | 3쪽 / 432 (562) / 100건 | 5쪽 / 720 (936) / 166건 |
| 100 | 4쪽 / 576 (749) / **266건** | 3쪽 / 432 (562) / 200건 | 5쪽 / 720 (936) / 333건 |

계산: 쪽 수 = 올림(1.5 x n / R) 이므로 n 상한 = 허용 쪽 수 x R / 1.5 의 내림이다. 쪽 수가 정해지면 정규 호출은 144 x 쪽 수, 여유 30%를 곱한 값이 괄호다. 900 이내인 가장 큰 쪽 수는 4쪽(749), 5쪽은 936으로 900을 넘는다. 700 이내는 3쪽(562), 4쪽은 749로 넘는다. 1,000 이내는 5쪽(936)이고 6쪽은 864 x 1.3 = 1,123이라 넘는다.
검증 예: R=100, n=266 -> 399/100 = 3.99 -> 4쪽 OK. n=267 -> 400.5 -> 5쪽이라 초과. R=10, n=26 -> 39/10 = 3.9 -> 4쪽 OK. n=27 -> 40.5 -> 5쪽.
겹침을 10분으로 줄이면(1.33배) 900 기준 상한이 R=100에서 300, R=10에서 30으로 오른다 [계산].

읽는 법: n이 "위험 900 기준 상한"을 넘으면 하루 중 호출이 900에 닿아 수집 간격이 자동으로 60분이 된다. "주의 700 기준" 상한을 넘으면 백필이 멈추고 경고가 온다(6-6). 즉 **백필까지 하려면 700 기준 상한 안**이어야 편하고, **30분 수집을 유지하려면 900 기준 상한 안**이어야 한다.

결론: R이 100 이상이면 종류별 30분 신규가 266건 안쪽까지는 개발계정으로 30분 수집이 유지된다(1,000 기준으로는 333건이지만 그 사이는 위험 단계에 걸린다). R이 작으면(10 안팎) 26건만 넘어도 개발계정으로는 모자라 운영계정 증량이나 개방표준 보조 수집이 필요하다. 이 판정은 D1 첫날에 n과 R을 재면 바로 나온다.

야간(예: 22시~06시)은 신규가 적을 것으로 보고 1시간 간격으로 줄이면 기본 호출을 더 줄일 수 있다 [추정].

### 6-6. 경고 임계치와 대응

| 단계 | 기준(하루 누적, 가정 한도 1,000) | 동작 |
|---|---|---|
| 주의 | 700회 도달 (70%) | 나에게 텔레그램 경고 1회. 백필 중단 |
| 위험 | 900회 도달 (90%) | 수집 간격을 60분으로 임시 확대, 경고 1회. **임시 조치이며 30분 결정을 바꾸는 것이 아니다. 다음 날 카운터가 초기화되면 30분으로 자동 복귀** |
| 중단 | 1,000회 근접 (정확한 한도 직전) | 호출 중단, 다음 날 초기화 후 6일 이하 조각으로 따라잡기 |

- 간격 60분은 사이클 안에서 "이번 사이클은 수집을 건너뜀"으로 구현한다(작업 스케줄러 설정은 그대로 30분).
- 카운터는 서비스 단위와 오퍼레이션 단위로 모두 기록한다(한도가 오퍼레이션별로 다를 수 있다는 사례 때문 [검색 요약]).
- 한도가 실제로 모자라면 대응 순서: (1) 페이지 크기 확대, (2) 겹침을 10분으로 줄이기, (3) 야간 간격 확대, (4) 개방표준서비스(일 10,000)를 보조 수집원으로 사용 검토, (5) 운영계정 증량 신청, (6) 수집 주기를 60분으로 완화.
- 증량 신청은 기본적으로 "일찍" 한다(15장). D0에서 등록 요건을 확인하고, 요건이 가벼우면 D1 실측 직후 바로 신청한다. D1~D3 중 한도 부족이 보이는데 등록 요건(공개 화면 등)이 아직 안 갖춰졌다면 (1)~(4)를 먼저 쓰고, 활용사례 등록에 쓸 최소 화면을 앞당길지 그때 판단한다.
- 고객이 늘어도 호출 수는 안 늘어난다. 수집은 한 번만 하고 매칭은 DB 안에서 하기 때문이다.

Windows 작업 스케줄러 사용 시 알아 둘 점 [추정, D1에서 시험]: (1) "사용자가 로그온할 때만 실행"으로 두면 비밀번호를 저장하지 않아도 되지만 PC가 로그아웃 상태면 돌지 않는다. (2) 절전·최대 절전 상태에서는 돌지 않으므로 PC 절전을 끈다. (3) PC가 꺼져 있다가 켜지면 "놓친 실행을 가능한 대로 빨리 시작" 옵션으로 한 번 따라잡는다. 그 뒤는 6일 조각 따라잡기가 처리한다.

이전 때 옮기는 것: 코드(git), `.env`(직접 옮김, git 금지), SQLite 백업 파일, 스케줄 설정. 같은 서비스키·봇 토큰을 PC와 VPS가 동시에 쓰면 호출 한도가 이중으로 소모되고 알림이 두 번 가므로, 이전하는 날 PC 쪽을 반드시 먼저 멈춘다.

### 10-1. 텔레그램 연결(`/start`) 구조 (A-5 해소)

상시 프로세스 없이 처리한다. 상시 프로세스를 두면 PC에서는 로그온 때 자동 시작·재시작 설정이, VPS에서는 서비스 등록이 추가로 필요하고 죽었는지 감시할 것도 늘기 때문에, 지인 3~5곳 규모에서는 비용이 효과보다 크다.

| 항목 | 규칙 |
|---|---|
| 방식 | 30분 사이클 맨 앞(4장 1번)에서 텔레그램의 "받은 메시지 가져오기"(getUpdates)를 한 번 호출해 새 메시지를 읽는다 |
| 연결 코드 | 계정마다 연결 코드를 발급한다(처음엔 설정 파일에 적음, D3 이후 웹에서 표시). 이용자는 봇에게 `/start 코드`를 보낸다. 코드가 맞으면 chat id를 channels에 저장하고 "연결됐습니다"라고 답한다. 코드가 없거나 틀리면 "연결 코드가 필요합니다"라고만 답하고 저장하지 않는다. 봇 아이디를 아는 아무나 내 계정에 붙는 것을 막기 위함 |
| 응답 지연 | 최대 30분. 이용자 안내문에 "연결 응답은 최대 30분 뒤에 옵니다"를 적는다 |
| 처리한 위치 | 마지막으로 처리한 메시지 번호를 settings(telegram_update_offset)에 저장해 같은 메시지를 두 번 처리하지 않는다 |

## 17. 용어 풀이

| 용어 | 쉬운 설명 |
|---|---|
| 오퍼레이션 | API가 하는 일 한 가지. 예: "물품 공고 목록 달라" |
| 서비스키 | 공공데이터포털이 내 프로그램에 주는 출입증 번호. 남에게 보이면 안 됨 |
| 개발계정/운영계정 | 개발계정은 시험용 낮은 한도, 운영계정은 활용사례를 등록하고 받는 높은 한도 |
| 증분 수집 | 지난번 이후 새로 올라온 것만 가져오기 |
| 겹침 | 증분 수집 때 지난번 끝 시각보다 조금 앞부터 다시 받는 것. 늦게 반영된 공고를 놓치지 않으려는 안전장치. 길수록 호출이 늘어남 |
| 백필 | 과거 데이터를 거슬러 올라가며 채우기 |
| 조각 | 조회기간 제한 때문에 한 번에 받을 수 있는 기간 덩어리(6일) |
| upsert | 있으면 고치고 없으면 새로 넣기. 같은 공고가 두 번 저장되지 않게 함 |
| 백오프 | 실패하면 기다렸다가 다시 시도하되 기다리는 시간을 점점 늘리는 방법 |
| 다이제스트 | 알림을 하루 2~3번 한 묶음으로 모아 보내는 방식 |
| 사이클(run_cycle) | 30분마다 한 번 실행되는 프로그램 한 바퀴. 텔레그램 확인 -> 수집 -> 매칭 -> 발송 순서 |
| 작업 스케줄러 | Windows가 정해진 시각에 프로그램을 자동 실행해 주는 기본 기능 (Linux 서버의 cron과 같은 역할) |
| cron | 정해진 시각에 프로그램을 자동으로 실행하는 서버 기능 |
| 상시 프로세스 | 한 번 켜서 계속 떠 있는 프로그램. 이 프로젝트는 웹(D3 이후)을 빼면 쓰지 않음 |
| getUpdates | 텔레그램 봇이 "나에게 온 새 메시지를 가져와 줘"라고 요청하는 기능 |
| 연결 코드 | 계정과 텔레그램 대화방을 안전하게 묶기 위해 `/start` 뒤에 붙이는 짧은 비밀 문자열 |
| 좁힌 조건 / 훑어보기 조건 | 키워드 등으로 좁힌 조건 / 종류만 정하고 다 보는 조건 |
| [화면 미확인] | 실제 화면을 열어 보지 않고 쓴 버튼·메뉴 이름이라는 표시. D0에서 맞춤 |
| VPS | 월 몇천~몇만 원에 빌리는 인터넷상의 작은 컴퓨터. 24시간 켜 두는 용도 |
| chat id | 텔레그램에서 "이 사람 대화방"을 가리키는 번호 |
| WAL | SQLite가 쓰는 동안에도 다른 프로그램이 읽을 수 있게 하는 모드 |
| 허용 목록 | 저장해도 되는 필드를 이름으로 정해 두고 나머지는 버리는 방식 |
| 정규식 | 전화번호·이메일처럼 정해진 모양의 글자를 찾는 검색 규칙 |
| 마스킹 | 비밀번호·키 같은 값을 `***`처럼 가려서 보이지 않게 하기 |
| totalCount / numOfRows | API 응답의 전체 건수 / 한 번에 받는 행 수(페이지 크기). 호출 횟수를 좌우함 |
| PG | 카드 결제를 대신 처리해 주는 회사(결제대행사) |
| 어댑터 | 알림 채널(텔레그램·이메일)마다 다른 부분을 감싸, 나머지 프로그램은 똑같이 쓰게 하는 연결 부품 |
