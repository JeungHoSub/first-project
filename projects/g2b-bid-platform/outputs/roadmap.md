# 입찰 플랫폼 로드맵 (roadmap) - 초안

작성: planner / 2026-11-12 / 짝 문서: spec.md
작업량은 "집중해서 하는 하루" 기준의 대략치이며 [추정]이다.

## 한눈에 보기

| 단계 | 이름 | 기간(대략) | 한 줄 목표 |
|---|---|---|---|
| 0 | 준비 | 1~2일 | 서비스키·조건 정하기 |
| 1 | 수집기 + DB | 3일 | 공고가 SQLite에 쌓인다 |
| 2 | 조건 매칭 + 텔레그램 알림 | 3일 | 내 조건 공고가 폰에 온다 (**MVP 완성**) |
| 3 | 간단한 웹 화면 | 3~4일 | 조건을 웹에서 고치고 공고를 본다 |
| 4 | 검수·안정화 | 2일 | 한 주 돌려 보고 버그·보안 정리 |
| 5 | 내가 쓰며 고도화 | 2~4주 | 마감 요약, 낙찰률 통계 등 필요한 것만 추가 |
| 6 | 판매 준비 | 1~2주 | 법·사업자·운영계정 정리 |
| 7 | 지인 파일럿 | 1~3개월 | 지인 3~5곳이 실제로 쓴다 |

MVP(단계 0~4)는 약 2주. 처음부터 계정 표(accounts/conditions)를 만들지만 화면에서는 나 한 명만 쓴다.

## 단계별 상세

### 단계 0. 준비

| 항목 | 내용 |
|---|---|
| 할 일 | 관심 업종·품목·지역 확정(spec 마지막 표). data.go.kr 가입, 입찰공고정보서비스 활용신청, 서비스키 발급. 텔레그램 봇 만들기(BotFather) |
| 담당 | 사용자(결정·발급) + planner(질문 정리) + researcher(공사·물품·외자 오퍼레이션명, 낙찰·사전규격 한도 확인) |
| 작업량 | 사용자 1~2시간 + researcher 반나절 |
| 완료 기준 | 서비스키가 `.env`에 들어가 있고(채팅에 노출 X), 조건 초안이 정해졌고, 사용할 오퍼레이션 목록이 g2b-bid-data 스킬에 반영됨 |

### 단계 1. 수집기 + DB

| 항목 | 내용 |
|---|---|
| 할 일 | 프로젝트 뼈대, SQLite 스키마(spec 6장), API 호출 래퍼(재시도·백오프), 증분 수집, (공고번호+차수) upsert, 일일 호출 카운터 |
| 담당 | developer |
| 작업량 | 약 3일 |
| 완료 기준 | cron으로 30분마다 돌고, 같은 공고가 중복 저장되지 않음. 최근 7일 공고가 DB에 있음. 하루 호출 수가 카운터로 확인되고 1,000건 이하. 서비스키가 코드·로그·git에 없음 |

### 단계 2. 조건 매칭 + 알림 (MVP 핵심)

| 항목 | 내용 |
|---|---|
| 할 일 | 조건 JSON 해석·매칭, 알림 기록(중복 방지), 채널 인터페이스 + 텔레그램 어댑터, 실패 재시도, 정정공고 라벨 |
| 담당 | developer (필요 시 skill-scout로 텔레그램 연동 스킬 확인) |
| 작업량 | 약 3일 |
| 완료 기준 | 내 조건에 맞는 새 공고가 텔레그램으로 오고 같은 공고가 두 번 오지 않음. 테스트 계정 2개를 만들어 서로 다른 조건으로 각자 다른 알림이 가는 것 확인 |

### 단계 3. 간단한 웹 화면

| 항목 | 내용 |
|---|---|
| 할 일 | 로그인, 조건 목록/편집/미리보기, 공고 목록(필터·마감순), 알림 내역, 채널 연결 설정 |
| 담당 | developer |
| 작업량 | 3~4일 |
| 완료 기준 | 웹에서 조건을 고치면 다음 수집부터 반영됨. 다른 계정의 조건·알림이 URL을 바꿔도 보이지 않음 |

### 단계 4. 검수·안정화

| 항목 | 내용 |
|---|---|
| 할 일 | 데이터 정확성(원문과 대조 샘플 20건), 계정 분리·비밀번호 해시·HTTPS·비밀값 노출 점검, 한도 초과 시 동작 점검, 백업 |
| 담당 | reviewer -> 사용자 검토(review/QUEUE.md) |
| 작업량 | 약 2일 + 내가 1주 실제 사용 |
| 완료 기준 | reviewer 지적 사항 해결, 1주간 놓친 공고가 없다고 내가 판단, 사용자 승인 |

### 단계 5. 내가 쓰며 고도화

필요한 것만, 한 번에 하나씩. 쓰다가 불편한 순서대로 정한다.

| 후보 | 담당 | 작업량 | 완료 기준 |
|---|---|---|---|
| 마감 임박 아침 요약 | developer | 1일 | 매일 아침 요약 도착 |
| 낙찰률 통계(참고용 문구 포함) | researcher(필드 확인) -> developer | 3~5일 | 업종·기관별 평균 낙찰률 표시, 참고용 고지 노출 |
| 관심 공고 저장·캘린더 | developer | 2~3일 | 저장한 공고의 마감 하루 전 알림 |
| 이메일 채널 | developer | 1일 | 어댑터 추가만으로 동작(구조 검증) |
| 사전규격 알림 | researcher -> developer | 2일 | 공고 전 규격 정보 알림 |
| 운영계정 전환 신청 | 사용자 + developer | 1~2시간 + 승인 대기 | 승인 후 일 한도 증가 확인(수치 기록) |

운영계정 신청은 판매 전에 꼭 필요하니 단계 4 직후 바로 시작하는 것을 권장한다(승인에 시간이 걸릴 수 있음).

### 단계 6. 판매 준비 (spec 11장 체크리스트)

| 항목 | 담당 | 작업량 | 완료 기준 |
|---|---|---|---|
| 공공데이터 이용허락범위·출처표시 확인 | researcher + 사용자 | 반나절 | 서비스별 상업 이용 가능 여부 문서화 |
| 사업자등록·결제 수단 | 사용자 | 며칠(행정 대기 포함) | 사업자번호, 결제 방식 정함(초기엔 계좌이체도 가능) |
| 개인정보처리방침·이용약관 초안 | content-writer 초안 -> 사용자 -> 전문가 검토 권장 | 2~3일 | 문서 게시, 화면에 참고용·누락 면책 고지 |
| 가격 확정(spec 12장) | planner + 사용자 | 반나절 | 요금제 1안 결정 |
| 계정 발급·온보딩 절차 | developer | 1~2일 | 지인 계정을 5분 안에 만들고 텔레그램 연결 가능 |
| 최종 검수 | reviewer -> 사용자 | 1~2일 | 계정 분리·보안·법 문구 체크 통과, 사용자 승인 |

### 단계 7. 지인 파일럿

| 항목 | 내용 |
|---|---|
| 할 일 | 지인 3~5곳 온보딩, 1~2주마다 피드백 수집, 요금 시범(무료 3개월 -> 유료 전환 여부), 불편 사항 반영 |
| 담당 | 사용자(영업·응대) + developer(수정) + planner(피드백 정리) |
| 작업량 | 주당 반나절~1일 [추정] |
| 완료 기준 | 3곳 이상이 한 달 이상 사용, 유료 전환 의사 확인. 월 원가(서버·수수료 약 3만 원 [추정]) 대비 수익 계산. 다음 확장(더 많은 업체) 여부 결정 |

## 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 개발계정 일 1,000건 초과 | 수집 중단 | 증분·큰 페이지·호출 카운터, 운영계정 조기 신청 |
| 오퍼레이션·필드 정보 부족(미확인) | 개발 지연 | 단계 0에서 researcher가 먼저 확인 |
| 공공데이터 상업 이용 조건이 막혀 있음 | 판매 불가 | 단계 6 이전에 확인, 안 되면 2단계 재검토 |
| 가격 경쟁력 약함(이비드 12개월 월 1.6만 원) | 판매 어려움 | 좁은 기능(텔레그램, 낙찰률)과 지인 네트워크로 승부 |
| 지인 지원 부담 | 내 시간 소모 | 파일럿 3~5곳으로 제한, 온보딩 절차 문서화 |
| 알림 누락 | 신뢰 하락 | 원문 링크·누락 고지, 한 주 이상 직접 검증 |
