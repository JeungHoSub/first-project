## 판정: 조건부 통과

N-1~N-7은 해소됐고 N-8은 한 항목만 부분 해소다. 호출량 표 32칸, 가격 퍼센트 8칸, 일정 합계, 손익분기를 모두 다시 계산했고 산수 오류는 문장 하나뿐이었다(직접 고침). brief 결정도 모두 반영됐다. 다만 백필 호출 수 예시가 낙관적이고(A-1), 방법 안내에 한 단계 여러 행동·모순이 남아 있다(A-3). D0 시작 전 문서 수정으로 충분하며 개발을 막지는 않는다.

## 2. 호출량 검산 (전부 재계산)

- 8행 x 4열 전부 일치. 예: R=10, n=50, 15분 = 올림(75/10)=8쪽 x 144 = 1,152 / R=100, n=300, 15분 = 올림(450/100)=5쪽 x 144 = 720 / 10분 = 올림(400/100)=4쪽 = 576 / 1시간 = 9쪽 = 1,296. 모두 맞음.
- 여유 30%: 720 x 1.2~1.3 = 864~936 맞음.
- n 상한(15분, 여유 30%, 1,000 이내): 5쪽 = 720, 936 이내 / 6쪽 = 864, x1.3 = 1,123 초과. 1.5n/R <= 5 이므로 R=10에서 n<=33.3 -> 33, R=100에서 333. 맞음.
- 6일 조각: 28일 = 4.67 -> 5조각이라 "4조각으로는 모자람" 맞음. 15P: P=10/30/100 -> 150/450/1,500 맞음.
- 일정 합계(D0~D2 9~10일, +이전 9.5~11일, D0~D4+이전 14.5~17일, +실사용 19.5~22일, 7~10주, 24~27주)와 손익분기(Basic 4곳, Plus 3곳) 모두 맞음.

## 4. 미확인 단정 점검

대체로 정직하다. 총괄이 curl로 직접 확인한 값만 [직접 확인]이고 트래픽 단위, numOfRows 최대, 공공누리·상업 이용·출처표시, 증량 수치는 미확인으로 남겼다. 예외는 A-3의 화면 문구(서비스키 안내의 버튼 이름·"Encoding/Decoding 두 종류")로, 직접 열어 본 적 없는 화면인데 근거 표시가 없다.

## 5. 새 지적

### 중간

**A-1. 백필 호출 수 예시(P=10/30/100)가 낙관적이고 예산과 맞지 않을 수 있다 (spec 6-4, roadmap D1)**
- P(조각당 페이지 수)는 변수라 했지만 R과 n에서 정해진다. 6일 = 288개 30분 구간이므로 한 종류의 6일치 행은 288n이고 P = 올림(288n/R)이다. 예: R=100, n=10이면 P=29, n=100이면 P=288. 6일 1조각만 받아도 3 x 288 = 864회라 "하루 최대 400회" 예산을 넘는다.
- 그러면 roadmap D1 완료 기준 "최근 6일 공고가 DB에 있음"은 하루에 안 끝날 수 있다.
- 제안: 6-4에 `P = 올림(288 x n / R)`를 적고, 예시를 n·R 조합으로 다시 쓰고, D1 완료 기준을 "백필 예산 안에서 며칠에 걸쳐 채움"으로 완화.

**A-2. n 상한 표가 spec 자신의 경고 임계치와 어긋난다 (spec 6-5 vs 6-6)**
- 상한 표는 1,000회 기준인데 5쪽 + 여유 30% = 936회는 위험 단계(900)이고 정규 호출만 720회라 주의 단계(700)도 넘는다. 상한 근처에서는 수집 간격이 자동으로 60분이 되고 백필은 멈춘다.
- 위험 단계(900)를 쓰면 4쪽 기준 상한은 R=100에서 n=266, R=10에서 n=26이다. 제안: 상한 표에 900 기준 열을 하나 더 두거나 "상한 근처에서는 6-6 경고가 먼저 울린다"를 적는다.

**A-3. 방법 안내(번호 단계) 잔여 문제 (roadmap)**
- 서비스키 3단계 "입력하고 로그인"(행동 2), 14단계 "열어 붙여 넣고 저장"(3), 봇 7단계 "붙여 넣고 저장"(2)은 더 나눌 수 있다.
- 13단계가 모순이다. "인증키 한 가지를 복사한다"고 하고 바로 "두 가지 모두 복사해 둔다"고 한다. 어디에 복사해 두는지도 없다. "Encoding 키를 복사한다 / Decoding 키를 복사한다"처럼 나누고 보관 위치를 쓸 것.
- 15단계는 4~14단계를 3개 서비스에 반복하라는 한 줄이다. 서비스마다 번호 단계를 쓰지 않아도 "검색어만 바꿔 4~14단계" 정도는 맞지만, 한 단계에 행동 여러 개라 스타일과 어긋난다. 1~3단계는 반복 불필요함을 적을 것.
- VPS 이전 단계 6(접속+설치), 7(만들기+붙여 넣기), 8(복사+열기), 12(확인+삭제)도 행동이 둘 이상. 단계 1·5도 "어디를 눌러야 하는지"가 없다(PC 운영체제가 D0에서 정해지므로 D0 뒤에 OS별로 다시 쓰겠다는 한 줄이 필요).
- data.go.kr 버튼·메뉴 이름은 직접 열어 본 화면이 아니다. "화면 문구는 다를 수 있음"에 더해 "[추정] 기억 기반, D0에서 실제 화면과 대조"를 적을 것.
- 유출 대처 서비스키 6단계(검색+삭제)도 나눌 것.

### 낮음

**A-4. 8장 bids 칸과 11-1 허용 표 불일치.** bids의 "업종" 칸은 개별 칸인데 11-1은 업종을 raw_json으로 둔다. bids의 "기초금액"은 허용 표에 후보가 없다(기초금액은 별도 오퍼레이션). "종류"는 필드가 아니라 호출한 오퍼레이션에서 오는 값이라는 한 줄 필요.

**A-5. `/start` 연결 응답 구조.** "연결됐습니다"라는 즉시 답장은 봇 메시지를 받는 상시 프로그램이 필요한데, 흐름도와 스케줄링(cron만)에는 없다. 30분 주기로 확인해 답하든 상시 프로세스를 두든 D2에서 정해야 한다.

**A-6. 정의 없는 말.** roadmap D4의 "전 업종 훑어보기 구역"은 spec에 없다. 일정 표 판매 결정 시점(6주차)과 "D5 끝 무렵"(6~8주차)도 약간 다르다. 7~10주 합계에는 영향 없음.

**A-7. 넓은 재확인 비용 미포함.** 6-3의 "하루 1회 24시간 재조회"(3 x 올림(48n/R)회)는 6-5 표·여유 30%에 들어 있지 않다. 필요해지면 R=100, n=100에서 144회가 추가된다는 한 줄을 권장.

**A-8. 운영체제 확인은 사용자가 글로 알려주는 방식.** choice-questions 원칙상 클릭 선택지로 받는 것이 낫다(아래 선택 질문).

## 6. 직접 고친 것 (1건, 산수 문장)

spec-v3.md 6-5 "읽는 법" 마지막 문장.
- 전: "R=10일 때는 n=10 이상이면 겹침과 상관없이 한도를 넘기 쉬워 ..."
- 후: "R=10일 때는 n이 33건(겹침 15분, 여유 30% 포함)만 넘어도 한도를 넘기 쉬워 ..."
- 이유: 같은 문서 표에서 R=10, n=10은 288회로 한도 안이고, 같은 절의 n 상한 표(33건)와 맞지 않았다.
- 나머지 오탈자는 찾지 못했다. 위 5장 지적은 내용 수정이라 제안만 남겼다. 숫자 오류는 이 한 문장 외에 없다.
