## 한 줄 요약

"내가 관심 있는 입찰 공고를 30분마다 모아 두었다가, 하루 2~3번 텔레그램 한 통으로 묶어 알려 주는" 작은 서비스를 먼저 내가 쓰고, 한 달 써 본 뒤 잘 되면 지인 업체에 싸게 판다. 데이터는 공식 API에서 무료로 받는다(이용허락범위 "제한 없음"·무료 [직접 확인], 단 공공누리 유형·출처표시 의무는 판매 전 최종 확인). 처음부터 계정별로 조건을 따로 저장해, 판매할 때 구조를 다시 만들지 않는다.

비유하면, 30분마다 우편물을 우체국에서 가져와 분류해 두고(수집), 하루 2~3번 각자 우편함에 한 묶음으로 넣어 주는 것(다이제스트)이다. 급한 우편(마감 임박)은 묶음 맨 위에 올려 놓는다. 우체국에 갈 때 "지난번에 가져온 시각보다 조금 앞부터" 달라고 하는 것이 겹침인데, 늦게 도착한 우편을 놓치지 않으려는 안전장치다. 이 겹침이 길수록 매번 받는 양이 늘어난다.

### 전 업종·전국이라 생기는 문제와 대응

전 업종·전국이면 조건이 사실상 "제한 없음"이라 묶음이 매우 길어질 수 있다. 하루 신규 공고 건수는 공식 통계를 못 찾았다(미확인). 실제 건수는 D1 첫날 totalCount로 잰다. 그동안의 안전장치는 위의 건수 상한(50건)과 맨 윗줄 요약이다. 쓰면서 제외어·키워드를 넣어 좁혀 간다.

### 대기 목록 상태

pending(발송 대기) -> sent(발송됨) / failed(실패 후 재시도 중) / expired(마감 지나 취소). 같은 (계정, 공고번호, 차수)는 한 번만 sent가 된다.

### 6-3. 증분 수집 설계 (조회기간 규칙 반영)

증분 수집 = 지난번 이후 새로 올라온 것만 가져오기.

| 항목 | 규칙 |
|---|---|
| 조회 구간 | 오퍼레이션별로 "마지막 성공 종료 시각 - 겹침"부터 "지금"까지. **겹침 기본 15분, 10~15분 범위에서 설정**(brief 결정). 한 번에 요청하는 구간은 약 40~45분 |
| 겹침 이유 | 등록 시각이 늦게 반영되는 공고를 놓치지 않기 위해. 겹친 만큼 같은 공고가 다시 오지만 (공고번호+차수) upsert로 중복이 사라진다 |
| 겹침을 줄인 대가 | 등록 반영이 겹침(10~15분)보다 더 늦은 공고는 놓칠 수 있다 [추정]. 그래서 D1에서 "공고일시와 처음 수집한 시각의 차이(등록 지연)"를 모두 기록하고, 하루 신규 중 지연이 15분을 넘는 건이 있는지 본다. 있으면 겹침을 늘리거나 하루 1회 넓은 재확인(최근 24시간 재조회, 호출은 3 x 올림(48n / R)회 [계산])을 넣는다 |
| 구간이 6일 초과일 때 | 내 PC가 꺼져 있었던 경우 등. 6일 이하 조각으로 잘라 오래된 것부터 차례로 따라잡기 |
| 기준 시각 종류 | 공고 게시일시 기준인지, 정정공고가 변경일시로도 조회되는지는 D0에서 확인(미확인). 정정을 놓치지 않는 방법이 핵심 |
| 완전성 검사 | 응답의 전체 건수(totalCount)와 실제로 받은 행 수를 비교, 다르면 해당 구간 다시 수집. (같은 구간 안의 누락만 잡는다. 늦게 등록된 공고는 위 등록 지연 기록으로 따로 본다) |
| 마지막 성공 시각 저장 | 구간 전체를 끝까지 받았을 때만 갱신(중간 실패 시 이전 값 유지) |
| 시간 기준 | 한국 시간(KST). 하루 카운터 초기화 시각은 자정으로 추정, D0에서 확인 |

### 6-4. 백필(과거 데이터 채우기) 설계

백필 = 과거 데이터를 한꺼번에 채우기. 조회기간 제한 때문에 "6일 조각 x 종류 3개 x 페이지 수"만큼 호출이 든다.

| 규칙 | 내용 |
|---|---|
| MVP 백필 범위 | 최근 6일치 1조각만(D0에서 7일 가능 확인 시 7일). 미리보기에 필요한 만큼 |
| 호출 수 공식 | 백필 호출 수 = 3종 x 조각 수 x 조각당 페이지 수 |
| 예산 | 정규 수집(6-5)을 먼저 확보하고, 경고 임계치 700회에서 그날 정규 호출 수를 뺀 만큼만, 하루 최대 400회까지 백필에 쓴다. 정규 수집이 700회에 가까운 날은 백필하지 않는다 |
| 낙찰률용 과거 데이터 | 낙찰정보 서비스는 한도가 따로(1,000)라 별도 예산으로 며칠에 걸쳐 진행 [추정]. 조회기간 규칙이 같은지는 D0 확인 9번 |

예시(조각당 페이지 수 P가 변수. 실제 값은 D1에서 측정): 약 28일 백필 = 3종 x 5조각(6일 조각이라 4조각으로는 모자람) x P = 15P회. P=10이면 150회, P=30이면 450회, P=100이면 1,500회(하루 한도 초과, 여러 날로 분할) [계산].

### 6-5. 하루 호출량 계산 (겹침 포함으로 다시 계산, N-1 해소)

전제: 개발계정 한도를 "하루 호출 횟수 1,000"으로 가정한다(단위는 미확인). 수집은 3종 x 하루 48회(30분마다).

- 기본 호출: 3 x 48 = 144회/일 [계산] (모든 호출이 1쪽으로 끝날 때)
- 매번 요청하는 구간 길이 = 30분 + 겹침. 그래서 한 번에 받을 행 수는 n이 아니라 (30 + 겹침) / 30 x n 이다.
  - 겹침 15분: 45/30 = 1.5배, 겹침 10분: 40/30 = 약 1.33배 [계산]
- 공식: **하루 호출 수 = 3 x 48 x 올림( (30 + 겹침) / 30 x n / R )**
  - n = 30분 사이 종류별 신규·수정 공고 수(미확인, 변수. 3종이 같다고 가정)
  - R = 한 페이지에 받는 행 수(numOfRows 최대값 미확인, 변수)

(모두 [계산]. n은 평균 가정이라 오전 몰림 시간대는 더 클 수 있음)

| R | n (종류별 30분 신규) | 겹침 없음(v2 표) | 겹침 10분 | **겹침 15분(기본)** | 겹침 1시간(v2 설계, 폐기) |
|---|---|---|---|---|---|
| 10 | 10건 | 144 | 288 | **288** | 432 |
| 10 | 50건 | 720 | 1,008 | **1,152** | 2,160 |
| 10 | 100건 | 1,440 | 2,016 | **2,160** | 4,320 |
| 10 | 300건 | 4,320 | 5,760 | **6,480** | 12,960 |
| 100 | 10건 | 144 | 144 | **144** | 144 |
| 100 | 50건 | 144 | 144 | **144** | 288 |
| 100 | 100건 | 144 | 288 | **288** | 432 |
| 100 | 300건 | 432 | 576 | **720** | 1,296 |

읽는 법: 겹침 1시간 열은 v2 설계를 그대로 계산한 값이다(R=100·n=300에서 1,296회로 한도 1,000 초과). 겹침을 15분으로 줄이면 같은 칸이 720회로 내려가고, 10분이면 576회다. R=10일 때는 n이 33건(겹침 15분, 여유 30% 포함)만 넘어도 한도를 넘기 쉬워 겹침 조정만으로는 해결되지 않는다(R 확인이 핵심).

여유 20~30%(정정·갱신 확인용)를 더하면 R=100, n=300, 겹침 15분은 720 x 1.2~1.3 = 864~936회라 경고 임계치(700, 900) 근처다.

한도 안에 드는 n의 상한 (겹침 15분, 여유 30% 포함, 하루 1,000회 이내) [계산]:

| R | 허용 쪽 수 | 호출 수 | n 상한(종류별 30분 신규) |
|---|---|---|---|
| 10 | 5쪽 | 720 (여유 포함 936) | 33건 |
| 100 | 5쪽 | 720 (여유 포함 936) | 333건 |

(6쪽이면 864회라 여유 30%를 더하면 1,000을 넘는다. 5쪽 기준으로 계산.)

결론: R이 100 이상이면 종류별 30분 신규가 300건 안쪽까지는 개발계정으로 버틴다. R이 작으면(10 안팎) 개발계정으로는 모자라고 운영계정 증량이나 개방표준 보조 수집이 필요하다. 이 판정은 D1 첫날에 n과 R을 재면 바로 나온다.

야간(예: 22시~06시)은 신규가 적을 것으로 보고 1시간 간격으로 줄이면 기본 호출을 더 줄일 수 있다 [추정].

### 6-6. 경고 임계치와 대응

| 단계 | 기준(하루 누적, 가정 한도 1,000) | 동작 |
|---|---|---|
| 주의 | 700회 도달 (70%) | 나에게 텔레그램 경고 1회. 백필 중단 |
| 위험 | 900회 도달 (90%) | 수집 간격을 60분으로 임시 확대, 경고 1회. **임시 조치이며 30분 결정을 바꾸는 것이 아니다. 다음 날 카운터가 초기화되면 30분으로 자동 복귀** |
| 중단 | 1,000회 근접 (정확한 한도 직전) | 호출 중단, 다음 날 초기화 후 6일 이하 조각으로 따라잡기 |

- 카운터는 서비스 단위와 오퍼레이션 단위로 모두 기록한다(한도가 오퍼레이션별로 다를 수 있다는 사례 때문 [검색 요약]).
- 한도가 실제로 모자라면 대응 순서: (1) 페이지 크기 확대, (2) 겹침을 10분으로 줄이기, (3) 야간 간격 확대, (4) 개방표준서비스(일 10,000)를 보조 수집원으로 사용 검토, (5) 운영계정 증량 신청, (6) 수집 주기를 60분으로 완화.
- 증량 신청은 기본적으로 "일찍" 한다(15장). D0에서 등록 요건을 확인하고, 요건이 가벼우면 D1 실측 직후 바로 신청한다. D1~D3 중 한도 부족이 보이는데 등록 요건(공개 화면 등)이 아직 안 갖춰졌다면 (1)~(4)를 먼저 쓰고, 활용사례 등록에 쓸 최소 화면을 앞당길지 그때 판단한다.
- 고객이 늘어도 호출 수는 안 늘어난다. 수집은 한 번만 하고 매칭은 DB 안에서 하기 때문이다.

## 7. 기술 선택안

| 영역 | 선택 | 이유 |
|---|---|---|
| 수집기 | Python | 재료가 풍부하고 단순 |
| DB | SQLite, **WAL 모드** | 수집기(쓰기)·발송기·웹(읽기·조건 편집)이 동시에 접근하므로. WAL = 쓰는 동안에도 읽을 수 있게 하는 SQLite 기능. 대기 시간(busy timeout)과 짧은 쓰기 트랜잭션도 설정. 백업은 SQLite 백업 기능 사용(파일 단순 복사 금지) |

#### (나) 자유 문장 안의 연락처

공고명(`bidNtceNm`)처럼 사람이 쓴 문장 필드에는 전화번호나 이메일이 섞여 들어올 수 있다. 저장 전에 정규식(글자 패턴 검사)으로 전화번호·이메일 모양을 찾아 `[연락처 가림]`으로 바꿔 저장한다. 원문이 필요하면 원문 링크로 본다.

- 검사 결과는 "0건"이 아니라 "**걸린 건을 사람이 확인**"으로 판정한다. 기관 대표번호처럼 개인정보가 아닌 것도 걸릴 수 있기 때문이다.
- 걸린 건은 로그에 공고번호와 건수만 남기고 내용은 남기지 않는다(로그에 연락처가 새는 것을 막기 위해).
- D0에서 실제 응답을 보고 자유 문장 필드가 어떤 것인지(공고명 외에 비고·참가자격 등이 목록 응답에 있는지) 정한다.

#### (라) D5 낙찰 서비스를 쓸 때의 추가 위험

낙찰정보를 받으면 낙찰 업체 정보가 새로 생긴다. 대표자 이름, 사업자번호, 주소·전화 계열 필드가 있을 수 있다(이름은 [추정], 예: `bidwinnrNm`, `bidwinnrCeoNm`, `bidwinnrBizno`). 개찰결과(`getOpengResultListInfo...`)에는 참가 업체 목록이 있어 같은 문제가 생길 수 있다. 개인사업자의 대표자 이름·주소·전화는 개인정보일 수 있으므로:

- 기본값: 업체명, 낙찰금액, 낙찰률, 개찰일만 허용. **대표자 이름·주소·전화는 제외.** 사업자번호는 개인사업자 여부에 따라 달라 보류.
- D5에서 낙찰 서비스를 쓰기 시작할 때 허용 목록 표를 **다시 만들고** reviewer가 점검한다. 확정은 D5 착수 전 실제 응답과 법 확인(일반 정보이며 전문가 확인 권장) 후.

1. 저장 후 점검: bids 전체에서 전화번호·이메일 모양 문자열을 정규식으로 찾아, 담당자 필드 계열은 0건, 자유 문장에서 걸린 것은 사람이 확인하는 점검을 D1 완료 기준과 D4 검수에 넣는다.
2. 이미 저장된 데이터 점검: DB 백업과 운영자(나) 열람에도 적용되므로 "화면에 안 보임"만으로는 부족하다. 저장 단계에서 제거한다.
3. 담당자 연락이 필요하면 원문 링크로 안내한다.

### 11-2. 비밀값 노출 방지 (M-1 해소)

data.go.kr API는 서비스키를 주소(URL)에 붙여 보내므로, 오류 로그에 주소가 통째로 찍히기 쉽다. 텔레그램 봇 토큰도 주소에 들어간다.

| 대책 | 내용 |
|---|---|
| 로그 마스킹 | 모든 로그·예외 메시지에서 `serviceKey=` 뒤 값과 `bot<토큰>` 부분을 `***`로 바꾸는 필터를 공통으로 적용 (마스킹 = 일부 글자를 가려 보이지 않게 하기) |
| 주소 통째 출력 금지 | 로그에는 오퍼레이션 이름과 조회 구간만 남기고 완성된 주소는 남기지 않음 |
| 라이브러리 로그 | HTTP 라이브러리의 상세(디버그) 로그를 꺼 둠 |
| 검사 | 로그 파일에서 키 앞부분을 검색해 0건인지 D1 완료 기준·D4 검수에서 확인 |
| 커밋 방지 | `.env`는 `.gitignore`, 저장소에는 `.env.example`(빈 값)만. 서비스키·토큰은 채팅에 붙이지 않는다 |
| VPS 이전 | `.env`는 git이 아니라 직접 옮기고, 옮긴 뒤 PC 쪽 사본을 지운다 |
| 유출 시 | roadmap-v3의 "유출 시 대처" 번호 단계(서비스키 / 봇 토큰 각각)를 따른다 |

| Plus | 14,900원 이하 | Basic + 조건 개수 확대, 낙찰률 참고 통계, 관심 공고·마감 일정 (S1에서 만든 것만 포함) |

경쟁사 비교(research-market-v2 4장 [계산], 경쟁사 요금은 [검색 요약]이며 공식 페이지 미열람. 인포21C는 구버전 자료에 27,500/284,000원이라는 다른 가격이 있어 시점 확인이 필요함):

| 우리 가격 | 인포21C 1개월 33,000 대비 | 인포21C 12개월 27,500 대비 | 이비드 1개월 21,000 대비 | 이비드 12개월 약 16,333 대비 |
|---|---|---|---|---|
| Basic 9,900 | 70.0% 낮음 | 64.0% 낮음 | 52.9% 낮음 | 39.4% 낮음 |
| Plus 14,900 | 54.8% 낮음 | 45.8% 낮음 | 29.0% 낮음 | 8.8% 낮음 |

- 해석(확인된 사실만): Basic 9,900원은 표의 모든 비교 대상보다 싸다. Plus 14,900원도 모두보다 싸지만 이비드 12개월 환산과는 8.8% 차이로 작다. 인포21C 1개월 요금 33,000원(검색 요약 기준) 대비로는 두 요금제 모두 절반 이하다(Plus는 약 45%). 다만 인포21C 12개월 요금 27,500원 대비로는 Plus가 절반을 넘는다(약 54%).
- 그래서 가격만으로는 차별이 약하고, 묶음 알림·낙찰률 같은 좁은 기능이 포인트다.
- 비드프로·지투비·키다리·비드큐 요금은 확인하지 못했으므로 "가장 싸다"고 홍보하지 않는다.
- 파일럿: 무료 3개월 후 유료 전환. 손익분기(월 원가 3만 원 [추정], 공급가 기준): Basic 9,000원 x 4곳 = 36,000원 -> 4곳. Plus 14,900원은 공급가 약 13,545원이라 3곳 [계산].
- Plus 정확한 금액(14,900 / 12,900 등)은 판매 준비(D6)에서 확정한다.

## 17. 용어 풀이

| 용어 | 쉬운 설명 |
|---|---|
| 오퍼레이션 | API가 하는 일 한 가지. 예: "물품 공고 목록 달라" |
| 서비스키 | 공공데이터포털이 내 프로그램에 주는 출입증 번호. 남에게 보이면 안 됨 |
| 개발계정/운영계정 | 개발계정은 시험용 낮은 한도, 운영계정은 활용사례를 등록하고 받는 높은 한도 |
| 증분 수집 | 지난번 이후 새로 올라온 것만 가져오기 |
| 겹침 | 증분 수집 때 지난번 끝 시각보다 조금 앞부터 다시 받는 것. 늦게 반영된 공고를 놓치지 않으려는 안전장치. 길수록 호출이 늘어남 |
| 백필 | 과거 데이터를 거슬러 올라가며 채우기 |
| upsert | 있으면 고치고 없으면 새로 넣기. 같은 공고가 두 번 저장되지 않게 함 |
| 백오프 | 실패하면 기다렸다가 다시 시도하되 기다리는 시간을 점점 늘리는 방법 |
| 다이제스트 | 알림을 하루 2~3번 한 묶음으로 모아 보내는 방식 |
| cron | 정해진 시각에 프로그램을 자동으로 실행하는 서버 기능 (Windows에서는 작업 스케줄러가 같은 역할) |
| VPS | 월 몇천~몇만 원에 빌리는 인터넷상의 작은 컴퓨터. 24시간 켜 두는 용도 |
| chat id | 텔레그램에서 "이 사람 대화방"을 가리키는 번호 |
| WAL | SQLite가 쓰는 동안에도 다른 프로그램이 읽을 수 있게 하는 모드 |
| 허용 목록 | 저장해도 되는 필드를 이름으로 정해 두고 나머지는 버리는 방식 |
| 정규식 | 전화번호·이메일처럼 정해진 모양의 글자를 찾는 검색 규칙 |
| 마스킹 | 비밀번호·키 같은 값을 `***`처럼 가려서 보이지 않게 하기 |
| totalCount / numOfRows | API 응답의 전체 건수 / 한 번에 받는 행 수(페이지 크기). 호출 횟수를 좌우함 |
| PG | 카드 결제를 대신 처리해 주는 회사(결제대행사) |
| 어댑터 | 알림 채널(텔레그램·이메일)마다 다른 부분을 감싸, 나머지 프로그램은 똑같이 쓰게 하는 연결 부품 |
