# 매직고스톱 기획 명세 (초안 v0.1)

> 작성: planner / 2026-11-12
> 규칙 세부는 `rules.md`(game-designer 작성) 참조. 여기서는 반복하지 않는다.

## 1. 한 줄 컨셉
"평소 하던 고스톱 그대로, 스위치 하나로 마법이 얹히는 게임."
매직을 끄면 그냥 정직한 고스톱, 켜면 판이 한 번씩 뒤집히는 맛이 생긴다.

## 2. 목표와 대상 사용자
- 목표: 기본 고스톱만으로 완성된 게임 + 켜고 끌 수 있는 매직 확장
- 대상: 고스톱 규칙을 아는 성인 캐주얼 유저. 돈 걸지 않고 가볍게 한 판 하고 싶은 사람
- 사용 상황: 출퇴근 중, 쉬는 시간에 브라우저에서 5~10분 한 판

## 3. 기본 가정 (brief 추천안 기준)
| 항목 | 가정 | 비고 |
|---|---|---|
| 플랫폼 | 웹(브라우저) 먼저 | 설치 없이 링크로 공유, 심사 부담 적음 |
| 대전 | AI 상대 1인용 먼저 | 서버 불필요 |
| 인원 | **2인 맞고** 먼저 (사용자 확인 필요) | AI 1명만 있으면 되어 가장 자연스러움. 3인 고스톱은 이후 확장 |
| 매직 종류 | MVP는 A(매직 카드) 하나만 | 아래 5절 근거 |

## 4. 엔진 설계 원칙: 매직이 기본 규칙을 건드리지 않게
개념만 적는다. 구현은 developer 몫.

- **두 층 구조**: 기본 규칙 엔진(패 분배·매칭·점수·고/스톱)은 매직의 존재를 모른다. 매직은 그 위에 얹는 별도 층.
- **이벤트 훅**: 엔진은 "패 분배 후", "내 차례 시작", "패 낸 뒤", "점수 계산 직전" 같은 지점에서 신호만 낸다. 매직 층이 그 신호를 듣고 반응한다.
- **수정자(modifier)**: 매직은 엔진 상태를 직접 고치지 않고 "점수 x2", "이 패 1장 공개" 같은 수정 요청을 낸다. 엔진이 규칙 검사를 거쳐 적용 여부를 결정한다.
- **끄면 완전 동일**: 매직 off일 때는 층 자체를 로드하지 않는다. 같은 시드(셔플 값)면 매직 없는 판 결과가 항상 같아야 하고, 이를 자동 테스트로 보장한다.
- **데이터 중심**: 매직 카드는 코드가 아니라 데이터(이름, 발동 시점, 효과)로 정의해 추가가 쉽게.
- 화면과 엔진도 분리해 두면, 나중에 모바일/멀티로 갈 때 재활용된다 (재활용 선호 반영).

## 5. 핵심 기능

### MVP (1~2주 목표)
1. 2인 맞고 한 판 완주: 패 분배, 바닥패 매칭, 뻑·따닥·쪽 등 기본 특수 상황, 점수 계산, 고/스톱 (세부는 rules.md)
2. AI 상대: 규칙을 지키는 기본 수준(쉬운 난이도 1단계)
3. 매직 카드 최소 3~4종, 매직 ON/OFF 토글
4. 게임 내 점수만 사용 (판돈·현금 개념 없음)
5. 웹 화면: 대전 화면 1개 + 시작/결과 화면

### 이후
- 3인 고스톱, 난이도 단계, 매직 카드 확장
- C 판 규칙 변형 이벤트 (엔진 구조상 매직 카드와 비슷해 비용 적음)
- B 캐릭터 스킬, D 성장·수집 (콘텐츠 양이 많아 후순위)
- 모바일 앱 포장, 온라인 멀티

### 제외 (MVP에서 안 함)
- 온라인 멀티, 계정/로그인, 서버
- 결제, 광고, 랭킹, 현금성 보상 (사행성 이슈로 아예 금지 항목)
- 성장/수집, 캐릭터 시스템

## 6. 매직 종류 추천
**추천: MVP는 A(매직 카드) 하나로 시작, 다음 C, 그 후 B/D.**

근거:
- A는 "판 중간에 쓰는 한 방"이라 재미가 바로 보이고, 이벤트 훅 구조를 검증하기에도 좋다.
- C는 같은 훅 구조로 거의 공짜로 붙일 수 있다 (엔진 변경 거의 없음).
- B/D는 밸런스·콘텐츠 양이 커서 MVP 일정에 안 맞는다.
- 먼저 매직 카드를 다 쓰면 판이 끝나기 전에 밸런스가 깨지기 쉬우니, 판당 사용 횟수 제한(예: 1~2장)을 기본으로 둔다.

MVP 매직 카드 예시(확정 아님, game-designer가 밸런스 검토): 상대 패 1장 보기 / 내 패 1장 교환 / 이번 판 점수 x2 / 바닥패 1장 뽑아오기

## 7. 화면과 흐름
```
시작 화면 (매직 ON/OFF 선택)
  -> 대전 화면 (내 패 / 바닥패 / 상대 획득패 / 점수 / 매직 카드 칸)
       - 내 차례: 패 선택 -> 매칭 -> 더미에서 뒤집기 -> (매직 카드 사용 가능 시점) -> 고/스톱
  -> 결과 화면 (점수 내역, 한 판 더)
```
- 매직 OFF면 매직 카드 칸이 아예 안 보인다.
- 규칙 설명(도움말) 한 장: 매직 효과 설명 포함.

## 8. 기술 선택안
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (추천)** | TypeScript + Vite, 엔진은 순수 로직 모듈, 화면은 가벼운 DOM/Canvas | 가볍고 테스트 쉬움, 정적 호스팅 | 애니메이션은 직접 |
| B | Phaser 등 2D 게임 프레임워크 | 애니메이션·에셋 편함 | 학습·번들 무게, 엔진 분리 신경 써야 함 |
| C | React + 상태관리 | UI 개발 빠름 | 카드 애니메이션 별도 작업 |

엔진·화면 분리 원칙은 어느 안이든 동일. 상태는 직렬화 가능하게 만들어 두면 멀티·리플레이 때 유리.

## 9. 비용 및 법적 위험 (한 칸 요약)
| 구분 | 내용 | 대응 |
|---|---|---|
| 비용 | 1인용 웹이라 서버 없음. 정적 호스팅 무료 티어로 월 0원 가능. API 요금 없음(AI는 규칙 기반). 도메인만 선택 사항(연 1~2만원) | 멀티 도입 시점에 재산정 |
| 사행성 | 현금·유료 판돈·환전·현금성 보상 금지. 게임 내 점수만. 점수를 사고파는 구조 없음. 앱 출시 시 등급 심사(게임물관리위원회 등급분류, 스토어 도박 관련 정책) 확인. 고스톱은 "사행성 게임 오해" 소지가 커서 웹 단계에서도 "현금 가치 없음" 문구 표시 | 결제/광고/랭킹 보상 제외, 출시 전 등급 기준 조사 |
| 저작권 | 화투 그림은 직접 만든/라이선스 확인된 이미지만 사용. 타사 고스톱 게임 UI/캐릭터 모방 금지 | 자체 일러스트 또는 무료 라이선스 에셋, 출처 기록 |
| 개인정보 | MVP는 로그인·수집 없음 | 분석 도구 도입 시 재검토 |

## 10. "확인 필요" 선택지 비교

### 1번 추가 기능 종류
| 선택지 | 개발 범위 | 일정 | 위험 | 재미 |
|---|---|---|---|---|
| **A 매직 카드 (추천 시작점)** | 카드 데이터 + 사용 UI + 훅 | 중 (3~4종이면 1주 내) | 밸런스(너무 강한 카드) | 판 중 반전, 직관적 |
| B 캐릭터 스킬 | 캐릭터 선택 + 스킬 + 일러스트 | 중~대 | 에셋 부담, 밸런스 | 개성, 반복 플레이 |
| C 판 규칙 변형 | 이벤트 풀 + 안내 표시 | 소 | 점수 기준 혼란 | 매판 새로움, 수동적 |

| B 모바일 앱 | 웹 + 포장/스토어 | +1~2주 | 스토어 등급·사행성 심사 | 터치 편함, 상시 접근 |
